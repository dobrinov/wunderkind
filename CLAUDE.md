# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Wunderkind is a Rails 8 app (Ruby 3.4, PostgreSQL) for math practice: students receive assignments of questions matched to their skill via an Elo rating system, earn XP/levels/streaks/badges, and questions support rich content with math notation and interactive widgets. UI copy is in Bulgarian with full i18n extraction (`config/locales/app.bg.yml` / `app.en.yml`, default locale `:bg`).

## Commands

- `bin/dev` — run the app (foreman: Rails server + `yarn build --watch` for JS + `bin/rails tailwindcss:watch` for CSS)
- `bin/rails db:prepare` / `bin/rails db:seed` — set up the database (seeds create admin@example.com and student@example.com, password `password`)
- `bundle exec rspec` — run tests; single file: `bundle exec rspec spec/services/elo_spec.rb`; single example: append `:LINE`
- `bin/rubocop` — lint (rubocop-rails-omakase); CI runs this plus `bin/brakeman --no-pager` (ignore file: `config/brakeman.ignore`)
- `yarn build` — bundle JS with esbuild into `app/assets/builds` (yarn 4, `nodeLinker: node-modules`)

## Architecture

Core answer flow: `AnswersController#create` delegates to `AnswerSubmission.call` (app/services/answer_submission.rb), which grades the response (`Grading`), updates per-topic skill ratings and the question's Elo (`Elo` module — dynamic K-factor, upset bonuses), awards XP (`Xp`, difficulty-scaled via Elo expected score), records the daily streak (`Streaks`), and awards badges (`Badges` — definitions in code, awards in `badge_awards`). `AnswersController#skip` → `AnswerSubmission.skip` is the "не съм го учил" (I haven't been taught this) path: it records a `user_answers.skipped` row that is neither right nor wrong, leaves the student's rating, XP, streak and badges alone, nudges the question's Elo up by `Elo.skip_adjustment` (an ordinary Elo loss for the question with a small K, so the bump is largest on questions rated at or below the student — the ones plainly mistagged), and defers the topic (`skills.deferred_until`, `AnswerSubmission::DEFERRAL_DAYS`, only for topics with fewer than `DEFERRAL_MAX_GAMES` games). Skips stay out of every count that measures effort or ability (`UserAnswer.attempted`, `Assignment#graded_questions_count` / `#score_percentage`, badges, `DailyPractice`'s median). `AssignmentCreator` builds assignments from published questions at the dispatcher's target difficulty, widening in Fibonacci steps; supports a `topics:` filter.

Content model: `Question#body` is a restricted ProseMirror-style JSON document (paragraph/text/bold/italic/math/hardBreak) rendered server-side by `RichContent` (KaTeX renders math client-side via the `math` Stimulus controller); `body_text` is the plain-text projection. `answer_type` enum: `multiple_choice` (options in `possible_answers` with a `correct` flag), `exact_value` (graded by `ExactValue` — fractions/decimals/percent/BG-comma equivalence, tolerance), `interactive` (widget state graded server-side by `Widgets` registry: number_line, ordering, fraction_bars — the solution never reaches the client), `free_text` (reserved, Phase 3 AI grading). `grading` jsonb holds expected value/widget params+solution. `status` enum: draft/private_library/in_review/published — only published questions enter practice. Legacy `text`/`answer` columns remain nullable until grading parity is confirmed in production, then drop.

Student home (`/calendar`, `CalendarsController#show`) is a hero CTA → duel card → homework → history, with a right rail of level ring / rating band / next badge. The month grid of `aspect-square` cells is gone (with it the `Calendar` service and the `shared/svg` partials): history is a nine-week contribution strip built by `PracticeHistory`, whose active days still link to that day's sessions. `RatingBand` names Elo ranges (Начинаещ/Уверен/Силен/Отличен/Състезател, the 1400 boundary shared with topic mastery) so a raw rating never leads on a student-facing screen. `Badges::Badge#progress` is an optional lambda over `Badges.stats_for(user)`, set only on countable badges, which drives the per-badge bars and `Badges.next_to_unlock`. `math_value`/`shared/_frac` (and `app/javascript/lib/frac.js` for the widgets) set a bare "3/4" as a stacked fraction so widget maths matches the typeset question body.

Users: `role` enum (student/teacher/parent/admin); role decides the landing page (`home_path_for`). Gamification state on users: `total_xp` (events in `xp_events`, level curve in `Levels`), `current_streak`/`longest_streak`/`streak_freezes` (logic in `Streaks`). Per-topic Elo lives in `skills` (user × topic); `users.elo` is the derived display value. Topics form a hierarchy via `parent_id`.

**There are no school grades anywhere in the model** — a first-grader who can do third-grade work gets it, and a fifth-grader who can't doesn't. `users.grade` and `questions.grade_min`/`grade_max` were dropped; difficulty is the question's Elo and ability is the student's, full stop.

Adaptivity (no AI/LLM integration — it was built and then removed by decision; question content is generated outside the app): `Dispatcher` (app/services/dispatcher.rb) is the single answer to "which problems suit this student right now" — it owns the pools (`practice_pool`, and `available_pool`, which drops topics the student has deferred by skipping), the difficulty target (`TARGET_SUCCESS_RATE` inverted through the Elo expectation, so the aim sits ~147 points below the student), the cold start (`starting_rating` = the 10th percentile of the published bank, applied by `User.new_student`; starting low is the cheap mistake), and calibration (`calibrating?` until `CALIBRATION_ANSWERS` attempted answers; `calibration_rungs` / `at_rung` build a ladder climbing `CALIBRATION_CLIMB` above the student). `SessionComposer` owns the *mix*, not the difficulty: a calibrating student gets `calibration_questions` (the ladder rotated across unlocked topics, so the curriculum graph still holds), everyone else gets spaced review due topics + frontier topics unlocked by `topic_prerequisites` + one stretch question + filler at the dispatcher's target. Two variety guards run there: `MAX_PER_TOPIC` spreads the frontier across topics, and `MAX_PER_SHAPE` (with the `diversify` pass, which recognises a template via `ProblemSeeds.shape_of`, mirrored in SQL as `SHAPE_SQL`) caps problems sharing one template — without it the arithmetic fact tables, being thousands of `a + b` rows in one topic, fill every young session; the cap yields rather than let a session shrink. `AnswerSubmission` schedules spaced review (SM-2-ish intervals on `skills`), detects topic mastery (rating ≥ 1400, ≥ 10 games → `mastered_at`, XP bonus), and halves XP for hinted correct answers. Hint ladders in `question_hints` are hand-authored and approved at `/overseer/questions/:id/hint`; only reviewed hints reach students. Free-text answers always record `verdict: pending_review` (`UserAnswer#pending_review?`, which the student-facing views treat as a fourth outcome beside right/wrong/skipped rather than as wrong); the homework assigner grades them via `AnswerOverridesController`. The global weekly leaderboard (`/leaderboard`) is nickname-only, Sofia-time Monday reset.

Challenges (live duels): `/challenges` pairs two students head-to-head on the same problems with one shared clock, scored on speed as well as correctness. `ChallengeMatchmaker` *is* the queue — an unmatched player is a `waiting` `Challenge` with one `challenge_participants` row, and the next player to press the button joins the closest lobby (within `MAX_GAP` rating points, or anyone who has waited past `PATIENCE`) and starts the match under a row lock; lobbies nobody joined inside `Challenge::LOBBY_TTL` are written off lazily, on the next matchmaking run or on the waiting player's own next poll. The problems come from `Dispatcher.pick_shared`, which aims at the midpoint of the two ratings and drops topics either player has deferred. `ChallengeScoring` pays `CORRECT_POINTS` for a correct answer plus up to `SPEED_POINTS` scaled by how much of the per-problem window was left, so a fast wrong answer is worth nothing and two correct answers always beat one. Durations are measured server-side from `challenge_participants.question_started_at` (stamped when a problem is served, cleared on answer), so the speed bonus can be neither forged by the client nor reset by reloading. `ChallengeSubmission` grades through `Grading`, pays XP per answer and records the daily streak, then finalizes when both players are done or the clock runs out — points decide it, a points tie goes to the lower total time, a tie on both (or a match nobody scored in) is a draw — awarding `Xp::CHALLENGE_WIN_BONUS`/`CHALLENGE_DRAW_BONUS`/`CHALLENGE_PLAY_BONUS` and the `duel_win`/`duel_wins_10` badges. A duel deliberately touches **no** measurement: no per-topic skill update, no question Elo, no `user_answers` row, so calibration and the dispatcher never read answers given under race conditions as evidence about a student. `ChallengeRecord` is a pure query over finished matches. The screens are driven by `challenge_controller.js` polling `GET /challenges/:id/state` (the app has no ActionCable setup); the server is the only authority on the clock, the scores and when a match ends, and opponents are shown by nickname only, like the leaderboard. Duels have no hints and no "не съм го учил" — both would be worth points to whoever used them fastest.

The landing page (`StaticPagesController#landingpage`, the `root`) is the one screen a visitor sees. Its artwork *is* the product: a real `.practice-card` with `.choice-button`s and a real `.fb-band` inside a `.landing-peek` frame, the student's own `shared/_rating_band_card`, and duel chrome — no illustrations and no stock photography, and amber appears in exactly one place, inside the screenshot, where it still means "you earned something". Every figure on the page is read off the constant that implements it (`Challenge::SECONDS_PER_QUESTION`, `ChallengeScoring::CORRECT_POINTS`/`SPEED_POINTS`, `DailyPractice::DEFAULT_MINUTES`, `Dispatcher::CALIBRATION_ANSWERS`/`TARGET_SUCCESS_RATE`, `AnswerSubmission::DEFERRAL_DAYS`, `RatingBand::BANDS`, `Widgets::REGISTRY`) so a claim cannot drift away from the code; the only query is the published-bank count, cached for a day, floored to a round hundred and swapped for the daily-minutes tile when the bank is too small to quote. There is no pricing, no usage metric and no testimonial, because none of the three exist yet. The `.landing-*` primitives and `.button-hero` are documented at `/design-system` under „Публична страница“.

Roles & social: teachers own `classrooms` (students join by `invite_code`; `Teachers::` namespace, application layout); parents link to children via `parent_links` (`users.link_code`, shown on the student profile; `Parents::` namespace). `HomeworkCreator` builds a `Homework` (+`homework_questions`) and materializes one resumable `kind: :homework` assignment per student — hand-picked from the assigner's library/published pool plus auto-fill near the group's Elo; results matrix via `Homework#completion_for`. `DailyPractice` sizes a `kind: :daily` session from `daily_minutes_target` and the student's median answer time. `Leaderboards.weekly_xp` is a pure query over `xp_events` (classroom boards, teacher-toggleable). Teacher questions are private by default; `submit_for_review` → admin queue at `Overseer::ReviewsController`. Email verification (`users.verified_at`, `generates_token_for`) gates teacher/parent mutations (`require_verified_email`); password reset via `PasswordResetsController`; mail through `UserMailer`.

Controllers: `AuthenticatedController` is the base for logged-in pages (session auth, `current_user` from `session[:user_id]`); auth endpoints are rate-limited. `Overseer::` is the admin area (`Overseer::BaseController` requires `current_user.admin?`, `admin` layout). Layouts: `application` (sticky nav, plus a `shared/_tabbar` bottom nav for students at phone widths), `modal` (answer flow), `landingpage` (the public marketing shell: header with Вход + Създай профил and section anchors, no app nav and no reward pills, plus the footer), `simple` (auth), all sharing `shared/_head`. The `modal` layout has two shapes: a page that sets `content_for :bare` owns all of its own chrome and gets a full-bleed gray page (the practice flow and duels, which supply `shared/_practice_header` or `challenges/_scoreboard`); anything else keeps the original white dialog with the back/close row. `back_path`/`close_path` params must pass through the `internal_path` helper (XSS guard).

Frontend: Turbo + Stimulus (controllers in `app/javascript/controllers`, registered in `index.js`), esbuild, Tailwind v4 (design tokens in `@theme` in `app/assets/tailwind/application.css`; every component rule lives in `@layer components` so a utility in the markup wins over what the component `@apply`s — unlayered rules outrank all utilities and used to silently beat them). Note esbuild's entry glob is `app/javascript/*.*`, so shared JS helpers go in a subdirectory (`app/javascript/lib/`) or they become their own bundle. Authoring uses Tiptap with a custom inline `math` node (KaTeX-rendered, MathLive popover editing) in `editor_controller.js`; students type exact-value answers via MathLive (`math_input_controller.js`, fonts in `public/mathlive-fonts`). KaTeX CSS/fonts are vendored in `app/assets/stylesheets`. The design system lives at `/design-system` (open in development, admin-only in production). No system tests are generated for this app.

Database: schema format is SQL (`db/structure.sql`). **The question bank ships empty.** Seeding creates users and the topic tree only: `db/seeds/topics.yml` (topics + prerequisite edges) is loaded by `ProblemSeeds.import_topics` via `rake topics:import`, which `db/seeds.rb` calls. Questions are authored in the admin UI or imported from a problem file with `rake problems:import FILE=path/to/problems.yml`. Two importable sets ship, neither at `problems.yml` (which `problems:export` overwrites): `db/seeds/starter_problems.yml` is a 100-problem dev/demo set (every leaf topic, all four answer types, all three widgets, ratings from 700 to 1450), and `db/seeds/arithmetic_facts.yml` is the 7,646 basic arithmetic facts — sums to 100, differences within 100, the 10×10 times table and its division facts, rated by size and carry/borrow. Problem files carry no grade keys; the importer ignores any that older files still have. The facts file is generated from a rule (the rule is in its header) rather than authored, and statements already in the starter set are omitted so the curated versions keep their explanations. Load either with `rake problems:import FILE=...`. Note that `problems:export` thins to `MAX_PER_SHAPE` per template, so an export is not a backup of the fact tables — re-import the file instead. `rake problems:export` writes the database back out (problems to `db/seeds/problems.yml`, the topic tree to `topics.yml`), thinning to `ProblemSeeds::MAX_PER_SHAPE` near-identical variants per problem shape. `rake problems:stats` reports the distribution. There are no problem generators — a parametric generator produced too many near-duplicates, and the curated seed set that replaced it was removed too; question content is authored outside the app. A fresh database therefore has no practice content until questions are added, so practice/homework flows will find an empty pool.

Deployment is via Kamal (`config/deploy.yml`) to wunderkind.bg; errors go to Sentry.

## Roadmap context

The product scoping doc (three phases: Foundation → Teachers/Classrooms/Homework → AI/adaptive path) is published as an artifact. All three phases are built (plus live duels, `/challenges`, added after them): Phase 1 (content model v2, gamification core, design system, platform cleanup), Phase 2 (teacher/parent roles, classrooms, homework, daily-minutes mode, email verification/password reset), Phase 3 (adaptive session composer + spaced review + topic mastery, hint ladders, teacher-graded free text, global weekly leaderboard). The Claude API integration Phase 3 originally included (hint generation, free-text grading, authoring assistant, review pre-check, budget cap) was removed afterward at the owner's request — questions are generated outside the app; the implementation lives in git history (commits `7d483cf`..`c15e459`) if it's ever wanted back. Not configured in production yet: SMTP delivery (verification/reset emails only log in development).
