# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Wunderkind is a Rails 8 app (Ruby 3.4, PostgreSQL) for math practice: students receive assignments of questions matched to their skill via an Elo rating system, earn XP/levels/streaks/badges, and questions support rich content with math notation and interactive widgets. UI copy is in Bulgarian with full i18n extraction (`config/locales/app.bg.yml` / `app.en.yml`, default locale `:bg`).

## Commands

- `bin/dev` — run the app (foreman: Rails server + `yarn build --watch` for JS + `bin/rails tailwindcss:watch` for CSS)
- `bin/rails db:prepare` / `bin/rails db:seed` — set up the database (seeds create admin@example.com and student@example.com, password `1`; in development, `db/seeds/development.rb` then simulates ~10 weeks of real usage through the actual services — a cast of students with history, streaks and badges, finished duels, question reports and a review queue; see its header for the cast, and note it takes a few minutes and only runs against an imported question bank)
- `bundle exec rspec` — run tests; single file: `bundle exec rspec spec/services/elo_spec.rb`; single example: append `:LINE`
- `bin/rubocop` — lint (rubocop-rails-omakase); CI runs this plus `bin/brakeman --no-pager` (ignore file: `config/brakeman.ignore`)
- `yarn e2e` — the Playwright suite (`yarn e2e:prepare` once first). It boots its own Rails server on port 3101 against its own `wunderkind_e2e` database and reseeds `lib/tasks/e2e.rake`'s fixture every run, so it never touches development data. The seed migrates that database first, because nothing else ever will and the first schema change after `e2e:prepare` would otherwise leave every spec failing on a 500 that looks like a broken feature. RSpec covers what the server decides; this covers what the browser does with it — Turbo, Stimulus, the polling duel screen, a `<dialog>` that needs `showModal`, the impersonation frame over five layouts. See `e2e/README.md`, including what it deliberately leaves out (MathLive, the widgets, sound)
- `yarn build` — bundle JS with esbuild into `app/assets/builds` (yarn 4, `nodeLinker: node-modules`)

## Architecture

Core answer flow: `AnswersController#create` delegates to `AnswerSubmission.call` (app/services/answer_submission.rb), which grades the response (`Grading`), updates per-topic skill ratings and the question's Elo (`Elo` module — dynamic K-factor, upset bonuses), awards XP (`Xp`, difficulty-scaled via Elo expected score), records the daily streak (`Streaks`), and awards badges (`Badges` — definitions in code, awards in `badge_awards`). `AnswersController#skip` → `AnswerSubmission.skip` is the "не съм го учил" (I haven't been taught this) path: it records a `user_answers.skipped` row that is neither right nor wrong, leaves the student's rating, XP, streak and badges alone, nudges the question's Elo up by `Elo.skip_adjustment` (an ordinary Elo loss for the question with a small K, so the bump is largest on questions rated at or below the student — the ones plainly mistagged), and defers the topic (`skills.deferred_until`, `AnswerSubmission::DEFERRAL_DAYS`, only for topics with fewer than `DEFERRAL_MAX_GAMES` games). Skips stay out of every count that measures effort or ability (`UserAnswer.attempted`, `Assignment#graded_questions_count` / `#score_percentage`, badges, `DailyPractice`'s median). A right or wrong answer also makes a sound — two synthesized notes each, rising for right and lower and falling for wrong, in `app/javascript/lib/sounds.js`; nothing ships as an audio file, and the cues are demoed audibly at `/design-system`. That cue is why `AnswersController#create` answers one POST two ways (`advance_to`): `format.html` redirects as it always did, `format.json` returns `{verdict, redirect}` for `answer_form_controller`'s `fetch`. The split is not decoration. Chrome hands a new document the previous one's user activation, but **WebKit and Firefox do not** — an `AudioContext` created on a freshly loaded page stays suspended with its `resume()` promise pending forever — so a chime played when the feedback page renders is silent on an iPad. The only page allowed to start audio is the one the student clicked on, so the answer is posted from it and it is left standing for the length of the cue before the next page is asked for. A skip and a `pending_review` answer carry no verdict and no sound, being neither right nor wrong. `users.sound_effects` is the switch, and it is one column in two places that therefore cannot disagree: the speaker button (`shared/_sound_toggle`, in the practice header and the duel scoreboard, saved by `SoundSettingsController` at `PATCH /profile/sound` — its own endpoint because `ProfilesController#update` would answer a mid-question press with a redirect and a „Успешно обновление!" toast) and a row in Настройки. With sound off the form submits natively exactly as before, and the fetch path never re-posts on failure — it reloads, because one answer per question is a database constraint and the POST may already have landed. Duels sound the same way, through `ChallengeAnswersController`. Every session is built by `SessionComposer` over `Dispatcher`'s pools; a session that cannot fill even after widening in Fibonacci steps (`Dispatcher::WIDENING_STEPS`) raises `Dispatcher::NotEnoughQuestions`. (The old `AssignmentCreator` module was deleted — it had no production callers, drew from `Question.published` directly and so would have bypassed `practice_pool`'s free-text and deferral rules if ever reconnected.)

A student can read their own record back at `/review` (`ReviewsController`, „За преговор"), two tabs over one shape: the questions they got wrong and the ones they marked „не съм го учил". `AnswerLog` is the query, and its whole point is that both lists are of *questions*, not of answers — nothing in `Dispatcher` excludes a question the student has already seen, so `user_answers.where(correct: false)` would keep a question got wrong in March and right in April on the list forever, which is the opposite of what the list is for. Only the latest answer to each question counts (`DISTINCT ON`, Postgres, which this app already is), so the list drains as the student fixes things and a question leaves it by being answered correctly. A `pending_review` free-text answer is excluded by name rather than by `correct: false` — it is waiting for a grader, not marked down. The mistakes tab offers `MistakePractice`, a session of `kind: :mistakes` built from those questions oldest-first (a mistake made this morning is still in mind; one made three weeks ago is the only one re-asking tells us anything about) and filtered through `practice_pool` but *not* through the deferral rules, because a wrong answer is not a skip and the student is the one choosing. That session is the one solo session that **measures nothing**: `Assignment#measured?` is false for it, and `AnswerSubmission` runs only its second half — grading, explanations, XP, streak, badges and the session bonus all happen, while the student's rating, the question's Elo, the `skills` row, its spaced-review date and its mastery do not move. The reason is the same one that keeps duels out of the measurements: these are questions whose worked explanation the student has already read, so a correct answer is recall, and recording it as ability would hand out rating for remembering an answer while telling the bank that a question only ever retried by the students who failed it is an easy one. Not moving the ratings is only half of that, which is what `UserAnswer.measured` is for: `attempted` means "not skipped" and is the *effort* scope (the history card, the accuracy, the badges, all of which a mistakes session genuinely earns), while `measured` additionally drops mistakes sessions and is read by the three places that take an answer as *evidence* — `Dispatcher.calibrating?`, the `player_games`/`task_games` K-factor, and `PerformanceTrend`, whose whole chart is "the difficulty of what you can get right" and would otherwise rise on recall. The XP has one carve-out for the same reason: `Xp::ATTEMPT_AMOUNT` buys the risk of attempting, an unmeasured session risks nothing, and a wrong answer there leaves the question on the list it came from — so a wrong answer in a mistakes session pays nothing, while a correct one pays in full and takes the question off the list. „Не съм го учил" is refused there too (`Assignment#skippable?`, enforced in `AnswersController#skip` and not only hidden in the markup) — the session has already been told, and a skip would move a genuine mistake off the list it was put on to drain. `PracticeHistory` gained a skip tally beside the answer counts: skips stay out of `total_answers`, the accuracy and the minutes (a skip is not practice and the daily goal is a goal for practice) but are counted as `total_skipped` and shown as the fourth stat on the history card, which is also the way through to `/review`. 

Content model: `Question#body` is a restricted ProseMirror-style JSON document (paragraph/text/bold/italic/math/hardBreak) rendered server-side by `RichContent` (KaTeX renders math client-side via the `math` Stimulus controller, except a `math` node that is nothing but a fraction of integers, which `RichContent` sets with the `.frac` stacked fraction instead — see the notation note below); `body_text` is the plain-text projection. Problem files are written in plain text, so `RichContent.text_to_doc` promotes every bare fraction in it (`RichContent::FRACTION`, guarded so `0,5/2`, `1/2/3` and `km/h` are left alone) to a `math` node: "1/2" is not how a fraction is written in a maths problem. `node_text` reverses it, so `body_text` still reads exactly as the source line — which matters, because that string is what the importer dedupes on and what `problems:export` writes back. Existing rows only gain the math nodes when their file is re-imported (`rake problems:import FILE=db/seeds/ladders/`, idempotent). `answer_type` enum: `multiple_choice` (options in `possible_answers` with a `correct` flag), `exact_value` (graded by `ExactValue` — fractions/decimals/percent/BG-comma equivalence, tolerance), `interactive` (widget state graded server-side by the `Widgets` registry — the solution never reaches the client). Twelve widgets ship: `number_line`, `angle_dial`, `clock_hands` and `coordinate_plot` place a value; `ordering` (dragged by its grip — on the right of the row, and it is the grip rather than the whole row that a finger drags, so the list does not swallow page scrolls — with pointer events, since no touch browser implements HTML5 drag and drop), `categorize` and `matcher` arrange; `multi_select` chooses; `blanks` and `grid_fill` fill in; `fraction_bars` and `grid_shade` shade. Each is a checker plus display in `app/services/widgets.rb` (plus a `solution_display` where the stored solution isn't shaped like a finished state — `multi_select` keys it `correct` rather than `selected`, and a counted `grid_shade` names no cells at all, so both would otherwise show an empty „верен отговор“ chip), a Stimulus controller in `app/javascript/controllers/widgets/`, a partial in `app/views/widgets/`, a hint string in the locales and a demo on `/design-system`. The authoring form can only build `QuestionFormParams::EDITABLE_WIDGETS` (number line, ordering, fraction bars); a question using any other widget keeps its stored grading when edited there, because those parameters are generated with the problem rather than typed, `free_text` (reserved, Phase 3 AI grading). `grading` jsonb holds expected value/widget params+solution. `status` enum: draft/private_library/in_review/published — only published questions enter practice. A question can carry one image on its polymorphic `attachable` (`QuestionImage`, an Active Storage attachment shown above the body in the practice, duel and preview views). Legacy `text`/`answer` columns remain nullable until grading parity is confirmed in production, then drop.

Students report broken questions: `question_reports` (question × user, `reason` enum — misleading / wrong_answer / missing_answer / typo / image / broken / other — plus an optional note, `status` open/resolved/dismissed and who closed it). The control is `shared/_report_problem`, a folded-away `<details>` under the answer controls on the practice screen (in both states — a wrong accepted answer is usually only discovered *after* answering) and on the review of a past answer; `QuestionReportsController#create` files it through `QuestionReport.file!`. Like a skip it is not an answer, and unlike a skip it is not even a measurement: reporting grades nothing, moves no Elo, XP, streak or `skills` row, and leaves the question answerable — the only consequence is a row in the admin queue, because the fix is always a human editing the question. A unique index on (question, user) means re-reporting rewrites the student's own row and reopens it rather than stacking duplicates, so the student sees what they said instead of a second form. `Overseer::QuestionReportsController` is keyed by *question*, not by report (`QuestionReport.open_questions`, newest complaint first): several students flagging one problem is one thing to read and one edit to make, so every action closes the whole pile — „Готово“ (resolved), „Няма проблем“ (dismissed) or „Скрий задачата“, which drops the question back to `draft`, the one status no practice session or duel draws from. The open count rides in the admin nav label, and the questions list flags reported rows. Duels report too, through `ChallengeReportsController` (`POST /challenges/:id/reports`) into the same rows and the same queue — reporting is not in the class of things a duel withholds (a hint and a skip would both be worth points to whoever used them fastest; a report awards nothing, skips nothing and stops nothing, so it costs the reporter their own seconds and nobody else's, which `reports.clock_note` says out loud). Mid-match the control sits under the answer controls on the problem in front of the player and comes back to it — re-serving does not re-stamp `question_started_at`, so the report buys no thinking time; on the result screen, the one place the whole match is listed with its answers, `challenges/_report` is a single control with a picker over the five problems (already-reported ones marked ⚑) rather than a flag on each row of a scoreboard. `shared/_report_reasons` is the shared body of every report form, so a duel and a practice question ask the same question in the same words.

Anyone signed in — student, parent or admin — can also *suggest* a problem: `/suggestions` (`SuggestionsController`, plus the `Suggestion` form model) is still a lighter door than the authoring editor — one topic, an optional explanation, no widgets, no status or Elo control — but it writes in the same language: the problem is typed in the same rich editor the admin form uses (`shared/_editor`, Tiptap + the inline math node), a picture can ride along (content-type checked, an ordinary `QuestionImage`), and the answer is either a value that must satisfy `ExactValue.parse` or a set of multiple-choice options (at least two, at least one marked correct). Bare fractions still come out as math nodes whichever way the problem arrives: an editor document goes through `RichContent.promote_fractions` (which walks the text nodes), a plain string — the seeds still speak in them — through `RichContent.text_to_doc`. It builds an ordinary question with `status: in_review`, so it lands in the admin review queue (which shows the options and the image, since approving unseen would be the bug); `elo` starts at the suggester's own rating (people propose problems from where they stand — a guess, so the queue card shows the Elo and links straight to the editor), and a duplicate of an existing `body_text` is refused the same way the importer dedupes. `questions.suggested_by_id` is separate from `author_id` on purpose: an authored question carries an author and no byline, but a suggestion is credited wherever it is asked — `shared/_suggested_by` renders „Предложи я: …“ (nickname first, real name only as a fallback, the leaderboard's privacy stance) in the practice-card meta row and on the duel card. The suggester follows their problems on the same page under waiting/accepted/returned — the internal draft/private_library statuses a rejection parks a question in are not their business.

Student home (`/calendar`, `CalendarsController#show`) is a hero CTA → duel card → goals → progress chart in one column, with a right rail of level ring / rating band / next badge, and the history strip and time chart across the foot. The trend chart sits *inside* the left column rather than under the whole grid: the rail is three cards tall whatever the student has done, and a student with no goal set left a hole the height of the difference. The nav calls it **„Начало"**, not „Календар" — the month grid that name described is long gone; the route is still `/calendar`, which is a URL nobody reads rather than a label everybody does. The month grid of `aspect-square` cells is gone (with it the `Calendar` service and the `shared/svg` partials): history is a nine-week contribution strip built by `PracticeHistory`, whose active days still link to that day's sessions, and above it the one chart on the page: `PerformanceTrend` plots the average Elo of the questions the student answered *correctly* each week over the same nine weeks. Deliberately not accuracy — `Dispatcher` holds every session near `TARGET_SUCCESS_RATE`, so percentage correct is engineered flat and would draw a horizontal line under a child who is improving; what moves is the difficulty. The gridlines are `RatingBand` boundaries rather than round numbers, so the axis reads in the same words as the band card and the raw Elo stays in the point's tooltip. A week the student sat out is a gap, not a zero, and the card does not render until two weeks carry a point. `RatingBand` names Elo ranges (Начинаещ/Уверен/Силен/Отличен/Състезател, the 1400 boundary shared with topic mastery) so a raw rating never leads on a student-facing screen. Its card draws the bar and the five names from the **same** numbers (`RatingBand.segments`, each band's share of the 800–1800 scale): they used to be a continuous gradient under five evenly-spaced flex items, so a rating of 1013 put the marker at 21% while „Уверен" — the band it is actually in — sat near 30%, and the dot landed to the left of its own label. Two axes drawn from different numbers can only agree by accident. `Badges::Badge#progress` is an optional lambda over `Badges.stats_for(user)`, set only on countable badges, which drives the per-badge bars and `Badges.next_to_unlock`. A badge is drawn as a **medal** (`shared/_medal`, the v2 design in `Badges.dc.html`): three things readable at a glance and none of them colour alone — the **shape** is the family (`Badges::FAMILIES`, one `clip-path` each), the **metal** is the tier (`Badges::TIERS` — bronze/silver/gold/legend, plus `special` for the one-offs that are not on a ladder, in violet enamel inside a gold rim), and the **engraved glyph and number** say what it is for. A locked medal keeps all three and fills from the bottom in its own metal tint (`--fill`), so the collection shows distance rather than absence — „412 от 500" is legible across a room where a 5px bar under a grey emoji was not. All CSS: there are no medal images. The glyphs are Lucide SVGs **vendored** into `app/assets/images/badges/` rather than masked off unpkg the way the design doc does, because this app serves its own assets; `Badges.glyphs` is checked against that directory by a spec, so a badge with a missing glyph fails rather than rendering blank. `secret: true` (`upset_win`, `comeback`) shows a padlock and „???" until earned — only for badges whose charm is the surprise, never for a goal a child could be working towards. The profile draws the collection as one **ladder per family** (`Badges.collection_for`), bronze to legend, with a „Съвсем близо" band (`Badges.closest_to_unlock`, the plural of `next_to_unlock`) and a `<dialog>` per badge showing its whole ladder; the ladder is fixed so „I'm two along the streak one" is a sentence about a place, where the old grid re-sorted itself by progress every day. Medals also carry the home rail's next badge, the post-session row and the profile header. The emoji survives as the medal's accessible name. The 36 further badges the design proposes — a `goals` family off the parent goals, `review_clear` off „За преговор", band and duel ladders — are **not** implemented, and `FAMILIES` deliberately does not list a family with no members: a constant naming something that does not exist is a comment pretending to be code, and an empty family renders an empty row. `math_value`/`shared/_frac` (and `app/javascript/lib/frac.js` for the widgets, and `RichContent.render_math` for question bodies) set a bare "3/4" as a stacked fraction so widget maths matches the typeset question body. All four write the same three spans on purpose: a question body and the multiple-choice options under it show fractions inches apart, and an option is a plain string with no document to hold a math node, so KaTeX in one and `.frac` in the other would put two different fractions on one card.

Goals and rewards: a parent can ask something of a child and promise something for it — `/parents/children/:id` is the observation space (`Parents::ChildrenController#show`), and it is the same performance cards the child sees on their own home page, because there is no second way of drawing nine weeks of practice and a parent sitting down with their child should be looking at the same picture (`calendars/_history` and `_time_spent` took `linked:`/`user:` locals for it; the active-day links and the review link are the student's own and are dropped on somebody else's page). A `Goal` is three columns out of one sentence — *fifteen minutes a day for a week, and you get an hour of Minecraft*: `metric` (minutes / problems / correct, all read off the **effort** scopes, so a mistakes session counts — a parent promising a reward for practice means practice), `mode` (`daily`, a bar to clear each day, or `total`, a running sum) and `period` (`week`/`month`, which come round again and pay again, or `once` with an end date). In `daily` mode `target` is a *count of days* and not „every day" on purpose: a goal a child loses for one bad Tuesday is a goal they stop trying for on Wednesday, and a parent who means every day sets seven. **Progress is never stored** — `Goals` asks `user_answers` the question afresh on every read, the way `PracticeHistory` does, and one `Goals::Tally` covers every period in one query. What *is* stored is `goal_awards`, one row per completed period, carrying a **copy** of the reward's wording: a parent who changes „an hour of Minecraft" to „an ice cream" next week has not changed what they owe for last week. Paying out happens on read (`Goals.refresh!`, from the calendar and the parent's page) rather than on answer — a session ends on the summary screen and lands on the calendar, which is a better place to be told you have earned something than the feedback card of whichever problem tipped the total, and it keeps `AnswerSubmission` out of this entirely; the unique index on (goal_id, period_start) is what makes a second look cost nothing. A goal is archived rather than edited — it is a promise made in particular words, and rewriting one mid-week changes what a child is working towards without telling them — and archiving never takes back what it already paid. The child's half is `calendars/_goals`, showing the parent's wording verbatim, which is the half that makes the feature work at all: a reward nobody told the child about motivates nobody. `Parents::RewardsController` marks one used, and only ever used — the list is a record of what a child earned and must not quietly lose an entry. 

Users: `role` enum (student/parent/admin — value 1 was teacher, retired when the role was removed and its users migrated to parent); role decides the landing page (`home_path_for`). Gamification state on users: `total_xp` (events in `xp_events`, level curve in `Levels`), `current_streak`/`longest_streak`/`streak_freezes` (logic in `Streaks`). Per-topic Elo lives in `skills` (user × topic); `users.elo` is the overall rating, updated per answer as its own Elo game against the question — never by adding the per-topic delta, which is measured against the topics' skill average: mixing the two baselines is the drift that once inflated improving students' ratings without bound. Topics form a hierarchy via `parent_id`.

**There are no school grades anywhere in the model** — a first-grader who can do third-grade work gets it, and a fifth-grader who can't doesn't. `users.grade` and `questions.grade_min`/`grade_max` were dropped; difficulty is the question's Elo and ability is the student's, full stop.

Adaptivity (no AI/LLM integration — it was built and then removed by decision; question content is generated outside the app): `Dispatcher` (app/services/dispatcher.rb) is the single answer to "which problems suit this student right now" — it owns the pools (`practice_pool`, and `available_pool`, which drops topics the student has deferred by skipping), the difficulty target (`TARGET_SUCCESS_RATE` inverted through the Elo expectation, so the aim sits ~147 points below the student), the cold start (`starting_rating` = the Elo of the easiest problem in the practice pool, applied by `User.new_student`; starting low is the cheap mistake, and the floor is the one point on the distribution that does not move as the bank grows — a percentile did), and calibration (`calibrating?` until `CALIBRATION_ANSWERS` *measured* answers and only while `users.placed_at` is nil; `calibration_rungs` / `at_rung` build a ladder climbing `CALIBRATION_CLIMB` above the student). A new student is placed *visibly* before any of that: `Placement` (app/services/placement.rb) runs an eight-question session of its own at sign-up and ends on a screen that names the student's band. It is an ordinary `Assignment` of `kind: :placement`, so the practice screen, the answer form, the sounds and the report control all work unchanged — the only thing it adds is choosing each next question from the answers so far. **Gallop, then bisect**: a pure binary search would open in the middle of the bank, which for most children is a problem they cannot read, so the first question sits near the floor and the step *doubles* (`CLIMB`) while answers are right; the first wrong answer closes a bracket and the rest of the session bisects it. That places a student within a few dozen Elo points across the whole 600-2800 range, and nobody is asked to start in the middle. A skip counts with the misses, because „не съм го учил“ is the honest answer to a topic school has not reached and reading it as „too hard for now“ beats making the child guess. The session is **unmeasured** (`Assignment::UNMEASURED_KINDS`, which `UserAnswer.measured` reads too, so the list cannot drift): its whole job is to find a rating, and letting the per-answer Elo run as well would move that rating twice by two different methods — but XP, the streak and badges are paid, because it is still eight problems a child sat down and did. `Placement.due?` is the one gate (`PlacementsController`, the home-page card and sign-up all ask it) and it is deliberately *not* „has no `placed_at`“: every account predating the feature has none, and replacing a rating hundreds of real answers converged on with an eight-question estimate would be a downgrade dressed as a feature — so it asks `Dispatcher.calibrating?`, which is the question „is this rating still a guess?“ and which `placed_at` already closes. `Assignment#complete?` exists for this kind: a placement is built one question at a time, so „nothing left unanswered“ is its state after *every* answer and cannot mean „finished“. Everything that reads the session reads `Placement.rows`, never the cached association — by the time `advance!` runs, the answer that triggered it was saved through a different instance of the same row, and a search that cannot see the last answer re-asks it and places everybody at the floor. Sign-up lands on `GET /placements/new`, a welcome screen that says what is about to happen (a redirect is a GET, and `create` is not); an abandoned session resumes rather than starting a second one (`Placement.unfinished`). The old invisible ladder is still underneath and still works, for anyone who skips the session. `SessionComposer` owns the *mix*, not the difficulty: a calibrating student gets `calibration_questions` (the ladder rotated across unlocked topics, so the curriculum graph still holds), everyone else gets spaced review due topics + frontier topics unlocked by `topic_prerequisites` + one stretch question + filler at the dispatcher's target. Two variety guards run there: `MAX_PER_TOPIC` spreads the frontier across topics, and `MAX_PER_SHAPE` (with the `diversify` pass, which recognises a template via `ProblemSeeds.shape_of`, mirrored in SQL as `SHAPE_SQL`) caps problems sharing one template — without it the arithmetic fact tables, being thousands of `a + b` rows in one topic, fill every young session; the cap yields rather than let a session shrink. `AnswerSubmission` schedules spaced review (SM-2-ish intervals on `skills`), detects topic mastery (rating ≥ 1400, ≥ 10 games → `mastered_at`, XP bonus), and halves XP for hinted correct answers. Hint ladders live in `question_hints` (a `ladder` of strings). The ladder never reaches the page: each click fetches one rung from `HintRevealsController` (`POST /questions/:question_id/hint`), which counts the reveal into `assignment_questions.hints_revealed` — the server-side number that halves a hinted correct answer's XP, taken from the row and never from the request, the same stance the duel clock takes on its speed bonus. Two ways in: typed at `/overseer/questions/:id/hint`, where `reviewed_at` gates them because a human is mid-edit, or shipped in a problem file's `hints:` key, which arrives reviewed — the answers and explanations beside them go live on import too, and 22.6k ladders were never going to be typed in one at a time. Families emit them with `c.q(hints: [...])`; `check.rb` refuses a rung that contains the answer, and 56 families (the puzzle, kangaroo and deduction ladders — 3.2k problems) carry one so far. **A hint is not a shortened explanation**: an explanation is read after a wrong answer and states the answer, a hint is read instead of giving up and must not. Availability is the *session's* choice, not the question's: `Assignment#hints_allowed?` reads the nullable `assignments.hints_allowed` if set, else `Assignment::HINTS_BY_KIND` (practice and daily yes). Duels never reach it — they have no assignment, and a hint would be worth points to whoever used it fastest. Free-text answers always record `verdict: pending_review` (`UserAnswer#pending_review?`, which the student-facing views treat as a fourth outcome beside right/wrong/skipped rather than as wrong); nothing serves free text today — the practice pool excludes it and the homework flow that carried it was removed — so the type is reserved for the Phase 3 AI grading. The global weekly leaderboard (`/leaderboard`) is nickname-only, Sofia-time Monday reset.

Challenges (live duels): `/challenges` pairs two students head-to-head on the same problems with one shared clock, scored on speed as well as correctness. `ChallengeMatchmaker` *is* the queue — an unmatched player is a `waiting` `Challenge` with one `challenge_participants` row, and the next player to press the button joins the closest lobby (within `MAX_GAP` rating points, or anyone who has waited past `PATIENCE`) under a row lock. Joining *fills* the lobby (`status: :lobby`) rather than starting the match: `ChallengeLobby` then runs the ready room, where both players press „Готов съм" and the last press stamps `starts_at` for a `COUNTDOWN_SECONDS` countdown, after which the next read flips it to `active` with `started_at = starts_at` — the countdown's own deadline, so the match clock is the same length for both players however late the poll that happened to start it was. There is no host and no start button, deliberately: the queue pairs strangers, and the one holding the only start button could sit on it. (A host button is the right shape for a room you invited a friend into; there is no such room yet.) The match used to begin the instant a second player arrived, which gave whoever had been waiting no moment to put their hands on the keyboard while the speed bonus was already running. Rooms nobody turns up to expire lazily on the way in — a lobby nobody joined inside `Challenge::LOBBY_TTL`, and a filled one nobody readied in inside `READY_TIMEOUT`. **Matchmaking runs on every poll of a waiting screen, not only on the button**, and `call` reaches past the player's own empty lobby to do it: treating that lobby as "a match you are already in" is what used to leave two people who pressed a second apart — or whose ratings were further than `MAX_GAP` apart on the first try — each sitting in a room of their own forever, with `PATIENCE` unable to rescue them because nothing ever looked again. Concurrency is the hard part of that, because a lock on one lobby cannot see a lock on another. Two guards: `candidates` lets a player who already holds a lobby join only an *older* one, so in any pair exactly one side qualifies and two waiting players cannot join each other; and `pair` locks **both players' user rows** in id order before seating anyone. The second is what makes "at most one match per player" hold at all — pairing is the one operation that commits somebody who is not the one asking (the host), so with three waiting lobbies A/B/C a player can be taking a seat in one while a third player takes a seat in theirs, and end up in two matches at once with somebody's opponent elsewhere. Every pairing either player is part of contends for the same row lock, which is where that is caught; ordering by id keeps it deadlock-free. A room both players readied in and then walked away from is written off by `ChallengeLobby.begin!` rather than started, since a match that is over before its first paint would otherwise pay both of them the draw bonus for a duel neither was at. A poll that moves a player into somebody else's room answers with a `redirect`, since the page they are on is no longer their match. The problems come from `Dispatcher.pick_shared`, which aims at the midpoint of the two ratings and drops topics either player has deferred. `ChallengeScoring` pays `CORRECT_POINTS` for a correct answer plus up to `SPEED_POINTS` scaled by how much of the per-problem window was left, so a fast wrong answer is worth nothing and two correct answers always beat one. Durations are measured server-side from `challenge_participants.question_started_at` (stamped when a problem is served, cleared on answer), so the speed bonus can be neither forged by the client nor reset by reloading. `ChallengeSubmission` grades through `Grading`, pays XP per answer and records the daily streak, then finalizes when both players are done or the clock runs out — points decide it, a points tie goes to the lower total time, a tie on both (or a match nobody scored in) is a draw — awarding `Xp::CHALLENGE_WIN_BONUS`/`CHALLENGE_DRAW_BONUS`/`CHALLENGE_PLAY_BONUS` and the `duel_win`/`duel_wins_10` badges. A duel deliberately touches **no** measurement: no per-topic skill update, no question Elo, no `user_answers` row, so calibration and the dispatcher never read answers given under race conditions as evidence about a student. `ChallengeRecord` is a pure query over finished matches. The screens are driven by `challenge_controller.js` polling `GET /challenges/:id/state` (the app has no ActionCable setup); the server is the only authority on the clock, the scores and when a match ends, and opponents are shown by nickname only, like the leaderboard. The duel surfaces carry the **v2 design** (`Duels.dc.html` in the Claude Design project): the scoreboard has its own band instead of borrowing the practice header — each player is a block, the shared clock is a `conic-gradient` ring whose fill *is* the time left (red under ten seconds), and one bar per problem replaces the dots. Under the stem sits the **speed meter**, which says „по-бързо = повече точки" rather than explaining it: the bar drains with the window the bonus is scored against and the number beside it is what answering this instant would pay. It is display only — `ChallengeScoring` still works the real figure out server-side from `question_started_at` — and it is drawn from the server's own `elapsed`, re-anchored on every poll, so a reload cannot make it read full again. The result screen compares the two players problem by problem with the seconds that earned the difference and marks the fastest correct answer in the match (computed in the view: it is a property of those five rows and of nothing else); a win gets confetti, seeded so reopening the screen from the history shows the same fall, and hidden under `prefers-reduced-motion`. These screens are also the first users of the v2 **ink** ramp (`--color-ink-*`, Tailwind's gray nudged toward the brand hue) and the tactile `--edge-*` shadows; the rest of the app is still on `gray-*` and moves across a screen at a time rather than in one sweep nobody can review. The v2 primitives are demoed at `/design-system` under „Двубой". Two things in the design were deliberately not taken: its searching copy says the match starts the instant somebody joins, which the ready room replaced, and its nav uses lucide icons from unpkg, which this app does not do — every asset is vendored. Duels have no hints and no "не съм го учил" — both would be worth points to whoever used them fastest.

The landing page (`StaticPagesController#landingpage`, the `root`) is the one screen a visitor sees. Its artwork *is* the product: a real `.practice-card` with `.choice-button`s and a real `.fb-band` inside a `.landing-peek` frame, the student's own `shared/_rating_band_card`, and duel chrome — no illustrations and no stock photography, and amber appears in exactly one place, inside the screenshot, where it still means "you earned something". Every figure on the page is read off the constant that implements it (`Challenge::SECONDS_PER_QUESTION`, `ChallengeScoring::CORRECT_POINTS`/`SPEED_POINTS`, `DailyPractice::DEFAULT_MINUTES`, `Dispatcher::CALIBRATION_ANSWERS`/`TARGET_SUCCESS_RATE`, `AnswerSubmission::DEFERRAL_DAYS`, `RatingBand::BANDS`, `Widgets::REGISTRY`) so a claim cannot drift away from the code; the only query is the published-bank count, cached for a day, floored to a round hundred and swapped for the daily-minutes tile when the bank is too small to quote. There is no pricing, no usage metric and no testimonial, because none of the three exist yet. The `.landing-*` primitives and `.button-hero` are documented at `/design-system` under „Публична страница“.

Search: the app is almost entirely behind a login, so `Seo` (app/services/seo.rb) makes `noindex, nofollow` the default and a page opts in with `seo title:, description:, canonical_path:, indexable: true` (the `SeoPage` concern, read by `shared/_head`). That default is not about leaking — the authenticated pages are unreachable without a session anyway — it is that a crawler following `/calendar` gets a redirect to `/sign-in`, and a dozen copies of the sign-in page is the whole of what a site this size gets crawled for. `robots.txt` and `sitemap.xml` are generated by `SitemapsController` rather than kept in `public/`, because both have to know which pages exist and a static file would go stale the first time a topic was added; a host that is not `Seo::DEFAULT_ORIGIN` closes itself to crawlers outright. The one public JSON-LD block is site-wide (`Seo.site_schema`), plus `FAQPage` on the landing page — mirroring the four FAQ entries that are actually rendered, from the same translation keys — and `Course`/`BreadcrumbList` on the content pages. `public/og-card.png` is the 1200×630 sharing card (Viber and Facebook groups, not Twitter); it is rasterized from `tools/og/card.html.erb` by `rake og_card:build`, an ERB template rendered inside Rails for the same reason the landing page reads its numbers off constants — the card once said „10 минути“ while `DailyPractice::DEFAULT_MINUTES` said 15, and a picture is the one surface where nobody would catch it.

Analytics: Plausible, loaded by `shared/_analytics` out of `shared/_head` (so all five layouts carry it) and switched by `Analytics.enabled?` — production only, and never for an admin, because the owner is the heaviest user of this app and on a site this size their own sessions and every `/overseer` page would be most of the dashboard. Signing out is how you check the script is live. The script is served from a first-party subdomain (`Analytics::SCRIPT_ORIGIN`, env-overridable) not because blockers are to be dodged but because a good share of parents run one and a dashboard that silently omits them is worse than none. Pageviews need no help — the script hooks `history.pushState`, which is what Turbo navigates with — but they do need `Analytics::PATH_NORMALIZER`, a `transformRequest` that folds any path segment of bare digits to `:id`: untouched, thirty thousand questions would be thirty thousand Top Pages rows of one visit each and the number that matters would not appear at all. Only bare digits, so `/matematika/3-klas` and `/matematika/tema/drobi` keep their own rows, which are the ones worth reading; the query string is kept whole, because Plausible reads utm_* off it and this product is shared by parents pasting links into Facebook groups. `Analytics::EVENTS` is the closed list of seven goals — a Plausible goal matches its name character for character, so the names live there and `track :session_started, kind: …` (the `TrackedEvents` concern) resolves one, raising on a typo rather than leaving a goal at zero for a month. An event rides the flash to the page the redirect lands on and is written into its `<head>` as a meta tag (provisional, so Turbo swaps it per visit where a `<script>` would pile up), read there by `lib/analytics.js` on `turbo:load`. `Duel Finished` is the one exception, sent from `challenge_controller.js` when the poll sees the status change, because that is the only moment that happens exactly once per player per match — a result screen can be reopened all week and a match can end on the clock with neither player making a request — and it goes through `trackThen`, which holds the reload until the event is away or 400ms have passed. Nothing sent carries a user id, a nickname or an email; every property is a low-cardinality enum already in the schema (role, session kind, report reason, duel result).

The public content pages (`CurriculumController`: `/matematika`, `/matematika/:n-klas`, `/matematika/tema/:slug`) are the part that can actually rank. The landing page can only ever rank for the brand, and a parent who has not heard of Wunderkind types „задачи по математика за 3 клас" instead — so these pages carry a real slice of the bank with the worked explanation under each problem, the answer on the page rather than behind a sign-up („с отговори" is the commonest thing a query adds), and links onward to every grade and topic. Samples are deterministic — a page that shows different problems on every fetch teaches a crawler not to cache it — and taken at evenly spaced points across the topic's *occupied* Elo window rather than off the front of it, since the first six of a six-thousand-problem range are the same problem in different numbers. Only multiple-choice and exact-value questions are shown: an interactive question's answer is a widget state with no reading as a line of text. `Topic#slug` is now a transliteration of the Bulgarian name through `Slug` (the official streamlined table, as in passports) — it used to be `SecureRandom.hex`, because `parameterize` folds Cyrillic to the empty string, which was harmless while nothing linked to a topic and useless the moment one became a URL.

`Curriculum` (app/services/curriculum.rb) is the grade ladder, and it is worth being blunt about why it exists at all, given that **there are no school grades anywhere in the model** and nothing above changes that: it is read by no part of the answer flow, stored on no user and no question, and lives entirely in the presentation layer. But every parent in the country searches in grades, and a site that refuses to say „клас" is a site they never find — so the public pages speak grades at the door and the app behind the door still speaks Elo. The grade→Elo windows are editorial and deliberately overlap, which is the same thing the app says once a child is inside; the topics on a grade page are measured off the bank (`MINIMUM_PER_TOPIC`) rather than off a curriculum document, so a page cannot promise a topic with no problems behind it. `/matematika/4-klas` and `/matematika/7-klas` carry an НВО section and put the exam in their title, because those are two queries with their own season.

Roles & social: **teachers, classrooms and homework were removed** (the `teacher` role, `Teachers::` namespace, classroom invites, `HomeworkCreator`, the `:homework` assignment kind and `AnswerOverridesController` are all gone; the drop migration converted teacher users to parents and their homework sessions to plain practice, so student history survived). Parents link to children via `parent_links` (`users.link_code`, shown on the student profile; `Parents::` namespace), and a child too young for an email gets a **managed account**: `User.create_managed_child!` makes a student with no email (`users.email` is nullable, presence required only `unless: :managed?`), a random unused password and `users.managed_by_id` pointing at the parent, plus the usual `parent_links` row. Such an account has no login of its own — it is reached by switching profiles (see Controllers). Creating a child with an email *and* password still works and is also managed, so the parent can switch in; a child linked by code is not managed and cannot be switched into, and an emailless child cannot be unmanaged (nobody would be able to reach them). `DailyPractice` sizes a `kind: :daily` session from `daily_minutes_target` and the student's median answer time. `Leaderboards.weekly_xp` is a pure query over `xp_events`, feeding the global weekly board. The `private_library`/`in_review` statuses and the admin review queue (`Overseer::ReviewsController`) remain — suggestions land there, and a rejection parks a question in them. Mail through `UserMailer` — but **the app sends none**, and `Mailing.enabled?` (`app/services/mailing.rb`, a single `false`) is the switch that says so, because both flows built on mail are only as good as the delivery under them. Email verification (`users.verified_at`, `generates_token_for`) gates parent mutations (`require_verified_email`): with the switch off nothing is sent on sign-up and `User#verified?` answers true whatever the column holds, so the gate, the `shared/_verification_notice` banner and its resend button go quiet together — one switch, because `verified?` is the only question any of them asks. Password reset (`PasswordResetsController`) is closed outright by a `require_mail_delivery` before_action, since every step of it *is* an email — the form sends a link, the link carries the token, the token is the only proof — and the sign-in page hides its „Забравена парола?" link, leaving the before_action to catch bookmarks with `password_reset.disabled`. What is left is changing your password from inside the app, where you have already proved who you are by signing in: `PasswordsController#update` (`PATCH /profile/password`, a section of the personal-data card on `/profile`) takes the current password, the new one and a confirmation, then rotates the session id and signs the same session back in. All three checks live in the controller because the model has an opinion about none of them — `has_secure_password` treats an empty `password=` as a no-op, so a blank field would otherwise report success and change nothing, and a typo'd new password would be unrecoverable without the confirmation. `User::MINIMUM_PASSWORD_LENGTH` is named so the form can say the number before the validation does. It refuses outright while a child's profile is open: `current_user` is the child there, whose password is random and unused, and the parent's is not what that screen is about. **A password genuinely forgotten still has no way back** — you have to be signed in to change one — so that door is a console until mail works. Everything else stays live behind the switch — routes, tokens, mailers, views, and `EmailVerificationsController#show`, so a link minted before the flip still stamps `verified_at`. Flip `Mailing::ENABLED` in the same change that configures delivery and both flows come back with nothing to rebuild.

Controllers: `AuthenticatedController` is the base for logged-in pages (session auth, `current_user` from `session[:user_id]`); auth endpoints are rate-limited. The session carries two identities: `signed_in_user` is whoever typed the password and `session[:child_id]` is the managed child whose profile is open, so `current_user` — what every other line of the app reads — is the child while a profile is open, and the practice, rating, XP and streak all land on the child. `ChildSessionsController` (`POST /switch-child/:id`, `DELETE /switch-child`) is the only way in and out; it re-checks `signed_in_user.managed_children` on *every* request rather than trusting the switch, `reset_session` on sign-in and sign-out drops any open profile, and while one is open the parent's own area is closed (`current_user` is a student) with `shared/_child_session_bar` in the `application` layout the only seam and the way back — it also lists the login's other managed profiles (`other_child_profiles`), because a household passes one device around and switching child should be one tap rather than a trip through the parent's own screens. An admin can also look at the app as somebody else: `/overseer/users` carries a „Прегледай" button per row and `ImpersonationsController` (`POST /impersonate/:id`, `DELETE /impersonate`, deliberately not under `/overseer` because *stopping* is pressed from inside a student's session where the admin area is shut) swaps `session[:user_id]` for the target and parks the admin's own id in `session[:impersonator_id]` — so every line of the app reads the viewed user as the signed-in one without a single conditional, and the two session mechanisms compose: an admin viewing a parent steps into that parent's managed children exactly as the parent would. Admins are not viewable, not for privilege reasons (admin is already the top role, so nothing escalates) but because the admin area is the one place a second impersonation could be started and a stack two deep has no obvious way back. It is **read-only**: `ApplicationController` refuses every non-GET request while a session is impersonated, because a graded answer given from this seat would move a real child's rating, spend their attempt and burn the question out of their assignment, and nothing afterwards could tell it apart from something the child did — this app measures children and must not measure the adult looking over their shoulder. The three exceptions write to the session and never to the database: signing out, switching child profile, and the stop button. The rule is on the verb, which cannot see the duel screens — a GET there serves a problem (stamping the player's clock, which their speed bonus is scored out of) and settles a match that ran out of clock (paying the bonuses and writing the result, since there is no job and a duel can expire with neither player making a request). Both are guarded at the write in `ChallengesController`. If the admin behind a session stops being one mid-session it is `reset_session`'d outright rather than left borrowed with nobody to hand it back to, and `shared/_analytics` measures `impersonator || current_user`, so the owner's heaviest clicking about still never reaches the Plausible dashboard. What it looks like is `shared/_impersonation_frame`, rendered as a direct child of `<body>` in all five layouts: one fixed red box over the viewport — fixed, so a long page cannot scroll the warning out of sight — with a bar naming the account, its role and the way out, and `body:has(> .impersonation-frame)` padding the page clear of it. Those rules are the one thing in the stylesheet that sits **outside** `@layer components` on purpose: a frame that any page could shift with a utility, or push its own content under, is a frame nobody can trust to be telling the truth about whose account this is. `Overseer::` is the admin area (`Overseer::BaseController` requires `current_user.admin?`, `admin` layout). Layouts: `application` (sticky nav, plus a `shared/_tabbar` bottom nav for students at phone widths), `modal` (answer flow), `landingpage` (the public marketing shell: header with Вход + Създай профил and section anchors, no app nav and no reward pills, plus the footer), `simple` (auth), all sharing `shared/_head`. The `modal` layout has two shapes: a page that sets `content_for :bare` owns all of its own chrome and gets a full-bleed gray page (the practice flow and duels, which supply `shared/_practice_header` or `challenges/_scoreboard`); anything else keeps the original white dialog with the back/close row. `back_path`/`close_path` params must pass through the `internal_path` helper (XSS guard).

What changed since you were last here: `config/changelog.yml` is the whole of it, read by `Changelog` and written by a person, with a version, a date and the entries in both locales. `users.last_changelog_version` holds the newest release that user has been *shown*; everything above it is unseen, and the `shared/_changelog_dialog` in the `application` layout lists it. A `<dialog>` and not a styled div, because only `showModal()` gives the top layer, the focus trap and an inert page, and this is a dialog in the strict sense; Esc and a backdrop click press the same button rather than closing silently, since a release note that can be dismissed without answering is one people learn to dismiss without reading. The button is a form, because the answer can only be remembered on the server — `PATCH /changelog` stamps the newest version there is, and `/changelog` is the page for going back and reading all of it, which stamps too (reading it *is* being told). Versions are compared with `Gem::Version` rather than counted, so "1.10.0" is newer than "1.9.0" and a column holding a version since deleted from the file still resolves; a column holding something that is not a version at all says nothing rather than everything. A new account is stamped current on create (`User` `before_create`), so a child signing up today is not greeted by a wall of releases they were never around for — NULL means the opposite, *nobody has ever told this person anything*, which is why every account predating the file gets the backlog once. Nothing is shown or stamped while an admin is impersonating: the notes are addressed to that person, and the only button is a write that session refuses. The file's own rules are in its header and guarded by `spec/requests/changelog_spec.rb` — ascending order, both locales filled, and no release note that mentions a controller, a migration or an Elo, because the audience is a ten-year-old and their parent. 

Frontend: Turbo + Stimulus (controllers in `app/javascript/controllers`, registered in `index.js`), esbuild, Tailwind v4 (design tokens in `@theme` in `app/assets/tailwind/application.css`; every component rule lives in `@layer components` so a utility in the markup wins over what the component `@apply`s — unlayered rules outrank all utilities and used to silently beat them). Note esbuild's entry glob is `app/javascript/*.*`, so shared JS helpers go in a subdirectory (`app/javascript/lib/`) or they become their own bundle. Authoring uses Tiptap with a custom inline `math` node (KaTeX-rendered, MathLive popover editing) in `editor_controller.js`; students type exact-value answers via MathLive (`math_input_controller.js`, fonts in `public/mathlive-fonts`) with a Bulgarian decimal comma and a cut-down keypad in place of MathLive's default layout, which opens on x, n, an integral sign and ∀∃; its ÷ key builds a stacked fraction, which is how ½ gets typed on a phone. MathLive serializes a fraction as `(1)/(2)` and a mixed number as `1(1)/(2)` — both the controller and `ExactValue.parse` unwrap that, because a child who reached for the fraction key typed no brackets and was being marked wrong for the serializer's. `answer_form_controller` claims Enter in the capture phase (MathLive treats it as its own commit key, and a widget's state sits in a hidden field with no implicit submission), except in a textarea, where it stays a newline and ⌘/Ctrl+Enter submits, and on the single-choice grid, where the form has no submit button because the option button *is* the answer. KaTeX CSS/fonts are vendored in `app/assets/stylesheets`. The design system lives at `/design-system` (open in development, admin-only in production). No system tests are generated for this app.

Database: schema format is SQL (`db/structure.sql`). Seeding creates users and the topic tree: `db/seeds/topics.yml` (topics + prerequisite edges) is loaded by `ProblemSeeds.import_topics` via `rake topics:import`, which `db/seeds.rb` calls; `db/seeds.rb` then imports the ladder corpus into an empty bank, so a fresh clone can run a practice session. Questions come from problem files: `rake problems:import FILE=path` takes a file **or a directory of them**. The bank that ships is about 30k questions across four sets, none at `problems.yml` (which `problems:export` overwrites): `db/seeds/ladders/` is the main corpus (22.9k problems in 21 area files, every leaf topic, Elo 600-2800, 12.8k of them interactive across all twelve widgets, 1,203 with a figure, worked step-by-step explanations on all of them); `db/seeds/authored_problems*.yml` are three earlier hand-written batches (~1k); `db/seeds/starter_problems.yml` is a 100-problem dev/demo set; and `db/seeds/arithmetic_facts.yml` is the 7,646 basic arithmetic facts (sums to 100, differences within 100, the 10x10 times table and its division facts), generated from the rule in its header rather than authored. Problem files carry no grade keys; the importer ignores any that older files still have. A problem row is `text`/`topic`/`elo`/`explanation` plus one of `answer` (+ optional `tolerance` for answers rounded with pi), `options` (multiple choice), `widget`, or `rubric`; `image` names a PNG relative to Rails.root and `image_filename` the name it is stored under. Unknown keys are ignored, which is why the ladder files can carry `family` for provenance.

The ladder corpus is built by `tools/authoring` (see its `README.md` for the commands and `PROBLEM_TYPES.md` for the catalogue of problem types and the recipe for adding more of each), which runs outside Rails: the app still has no question generator in it and never makes a question at runtime. A *family* there is one type of problem written at six rising Elo ratings with a few variants each, so a student who cannot do a type meets the same type lower down and climbs back up as their rating recovers — `spec/services/ladder_corpus_spec.rb` guards that property, along with answer parseability, figure files and explanation depth. Rebuild with `ruby tools/authoring/build.rb`, then `tools/authoring/rasterize.sh` (headless Chrome turns the figure SVGs into PNGs — Active Storage will not serve SVG inline), then `ruby tools/authoring/check.rb`, which validates answer parseability, widget shapes (values on the step grid, points inside the plane, bins that are not empty), figure files and explanation depth. Figures are drawn to scale from the numbers in the question, and every number in a figure is repeated in the text because the views render question images with an empty `alt`.

Note that `problems:export` thins to `MAX_PER_SHAPE` per template and drops images and `family`, so an export is not a backup of the fact tables or the ladder corpus — re-import the files instead. `rake problems:export` writes the database back out (problems to `db/seeds/problems.yml`, the topic tree to `topics.yml`). `rake problems:stats` reports the distribution. The earlier parametric generator was removed for producing near-duplicates; the ladder builder answers that with families whose variants are capped per rung and deduplicated against the whole corpus and the existing bank.

Deployment is a shell script on the box, not Kamal — the `kamal` gem, `config/deploy.yml` and `.kamal/` were removed, because they described an arm64 host, a Docker Hub registry and a `kamal-proxy` that production has never had, and a deploy config that is fiction is worse than none. The real thing: wunderkind.bg is one x86_64 host shared with another app, and `/opt/apps/wunderkind/deploy.sh [branch]` (default `main`) fetches from GitHub into `src/`, runs `docker compose build` and `up -d` against `/opt/apps/wunderkind/compose.yaml`, then waits on the container healthcheck. **Migrations need no separate step** — `bin/docker-entrypoint` runs `db:prepare` whenever the command is `rails server`, so they apply on boot. There is no `config/master.key` anywhere: secrets are plain env in `/opt/apps/wunderkind/.env` (`SECRET_KEY_BASE`, `POSTGRES_PASSWORD`), which is why a clone can run the app but cannot decrypt `credentials.yml.enc`. A shared Caddy (`/opt/infra/caddy`) terminates TLS on the `edge` network and 301s www to the bare host — one reason `Seo.origin` is a single string — and a shared Postgres sits on `internal`. `/opt/infra/backup.sh` dumps every database nightly to `/opt/backups`; run it before a migration that rewrites rows. `bin/thrust` still fronts Rails in the image, so the `thruster` gem stays. Errors go to Sentry.

## Roadmap context

The product scoping doc (three phases: Foundation → Teachers/Classrooms/Homework → AI/adaptive path) is published as an artifact.
