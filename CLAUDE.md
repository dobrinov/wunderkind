# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Wunderkind is a Rails 8 app (Ruby 3.4, PostgreSQL) for math practice: students receive assignments of questions matched to their skill via an Elo rating system, earn XP/levels/streaks/badges, and questions support rich content with math notation and interactive widgets. UI copy is in Bulgarian with full i18n extraction (`config/locales/app.bg.yml` / `app.en.yml`, default locale `:bg`). The app stores no one's gender, so Bulgarian copy about the reader or a named person is written to fit anyone: no „го“/„му“/„той“ for a person, and no masculine past participle addressed to the reader („си решил“, „не съм го учил“ — the skip button is „Още не сме го учили“, the duel's ready button „Давай!“). Rephrase with the aorist („стигна“), a plural, or a noun instead of writing „(а)“; a generic noun („ученик“, „родителят“) is fine.

## Commands

- `bin/dev` — run the app (foreman: Rails server + `yarn build --watch` for JS + `bin/rails tailwindcss:watch` for CSS)
- `bin/rails db:prepare` / `bin/rails db:seed` — set up the database (seeds create admin@example.com and student@example.com, password `1`; in development, `db/seeds/development.rb` then simulates ~10 weeks of real usage through the actual services — a cast of students with history, streaks and badges, finished duels, question reports and a review queue; see its header for the cast, and note it takes a few minutes and only runs against an imported question bank)
- `bundle exec rspec` — run tests; single file: `bundle exec rspec spec/services/elo_spec.rb`; single example: append `:LINE`
- `bin/rubocop` — lint (rubocop-rails-omakase); CI runs this plus `bin/brakeman --no-pager` (ignore file: `config/brakeman.ignore`). `bin/brakeman` passes `--ensure-latest`, so a new Brakeman release fails CI until `bundle update brakeman`. CI's runner is pinned to `ubuntu-24.04` because newer images only build the latest Ruby patch and `.ruby-version` (3.4.2) is what the production image uses. The app runs Rails 8.1 on `load_defaults 8.1`, and `brakeman.ignore` is empty
- `yarn e2e` — the Playwright suite (`yarn e2e:prepare` once first). It boots its own Rails server on port 3101 against its own `wunderkind_e2e` database and reseeds `lib/tasks/e2e.rake`'s fixture every run, so it never touches development data. The server command migrates that database before it boots (and the seed migrates again), because nothing else ever will, and Playwright polls the server before it runs the seed — after any schema change the run used to die on a pending-migration 500 that looked like a broken server. `E2E=1` switches off the schema dump for those migrations (`config/environments/development.rb`), or every run would rewrite `db/structure.sql` from the e2e database. Two projects: `chromium` runs everything, and `ipad` (WebKit as an iPad Pro with touch) re-runs the scratch paper and `ipad.spec.mjs` — a finger stroke, a tapped editor key keeping the text box focused — because those live or die on Safari's touch handling (a refused touch `pointerdown` cancels the tap, which once left every editor key dead on an iPad). RSpec covers what the server decides; this covers what the browser does with it — Turbo, Stimulus, the polling duel screen, a `<dialog>` that needs `showModal`, the impersonation frame over five layouts. See `e2e/README.md`, including what it deliberately leaves out (MathLive, the widgets, sound)
- `yarn build` — bundle JS with esbuild into `app/assets/builds` (yarn 4, `nodeLinker: node-modules`)

## Architecture

The detail for each area lives in a path-scoped rule file under `.claude/rules/`, which Claude Code loads when files matching its `paths:` are touched. **When working in an area its paths do not cover, read the file first.** When documenting a new feature, add it to the matching rule file (extend its `paths:` if new files belong to it), not here — this file is loaded into every session and has a size budget (`spec/docs/claude_md_spec.rb`).

- `.claude/rules/practice-screen.md` — The practice screen: answer sounds and the JSON/HTML split, feedback card, landscape layout, „Чернова“, „Прочети ми“, the session summary
- `.claude/rules/practice-modes.md` — Practice modes: topics, problem types, review: „Тренирай тема“, „Типови задачи“, „За преговор“ and the mistakes session that measures nothing
- `.claude/rules/content-and-bank.md` — Question content, widgets and the admin bank: RichContent, ExactValue, the twenty widgets, statuses, images; the admin question browser/editor, regrades, revisions
- `.claude/rules/reports-and-suggestions.md` — Reports, suggestions and the inbox: question reports as tickets, threads, suggested problems, „Входящи“ and review mode
- `.claude/rules/navigation-and-home.md` — Navigation, feature rollout, „Днес“ and „Аз“: the one menu, workspaces for admin-parents, FeatureVisibility, the home page, progress, RatingBand, coins
- `.claude/rules/parents-and-families.md` — Parents, families, goals, focus: goals and rewards, „Какво упражнява“, managed children, co-parents, session length, stale sessions
- `.claude/rules/mail-and-accounts.md` — Mail and accounts: the SMTP switch, verification, password reset, the weekly report, the child reminder, email preferences
- `.claude/rules/adaptivity.md` — Adaptivity: Dispatcher, grade hold, placement: pools, targets, calibration, placement's gallop-then-bisect, SessionComposer's mix, hints, the school-grade hold
- `.claude/rules/duels.md` — Duels: matchmaking and its locks, the ready room, scoring, lobbies, invitation rooms, rematches, the v2 duel design
- `.claude/rules/friends-and-leagues.md` — Friends and leagues: friend codes, presence, effort-ranked leagues, nicknames
- `.claude/rules/public-pages-and-analytics.md` — Public pages, SEO, analytics, admin stats: landing page, Seo/sitemap, Plausible + Trace, admin statistics, /matematika grade and topic pages, explainers, Curriculum
- `.claude/rules/competitions.md` — Competitions, exams and past papers: the calendar data, public competition pages, entries, „Подготви се“, mock exams, past papers and modelled problems
- `.claude/rules/sessions-and-impersonation.md` — Controllers, child profiles, impersonation, changelog: signed_in_user vs current_user, switching into a child, read-only impersonation, admin people pages, layouts, the release-notes dialog
- `.claude/rules/frontend.md` — Frontend and the design system: Stimulus/esbuild/Tailwind v4 rules, the one-of-each components, type and radius scales, the number pad, lazy KaTeX
- `.claude/rules/ladder-corpus.md` — The ladder corpus and problem files: tools/authoring families, build/rasterize/check, held families, splicing a one-family rebuild

Core answer flow: `AnswersController#create` delegates to `AnswerSubmission.call` (app/services/answer_submission.rb), which grades the response (`Grading`), updates per-topic skill ratings and the question's Elo (`Elo` module — dynamic K-factor, upset bonuses), awards XP (`Xp`, difficulty-scaled via Elo expected score), records the daily streak (`Streaks`), and awards badges (`Badges` — definitions in code, awards in `badge_awards`). `AnswersController#skip` → `AnswerSubmission.skip` is the "не съм го учил" (I haven't been taught this) path: it records a `user_answers.skipped` row that is neither right nor wrong, leaves the student's rating, XP, streak and badges alone, nudges the question's Elo up by `Elo.skip_adjustment` (an ordinary Elo loss for the question with a small K, so the bump is largest on questions rated at or below the student — the ones plainly mistagged), and defers the topic (`skills.deferred_until`, `AnswerSubmission::DEFERRAL_DAYS`, only for topics with fewer than `DEFERRAL_MAX_GAMES` games) — and, whatever the topic's history, the problem *type*: `Dispatcher.deferred_shapes` reads the student's skips of the last `DEFERRAL_DAYS` and `available_pool`/`pick_shared` drop every question of the same template (`SessionComposer::SHAPE_SQL`, the text with its numbers blanked). Broad topics like „Умножение и деление" hold both what a child knows and what school has not reached, so the topic rule never fired on them, and a third of production's skips were a type skipped again within three weeks. Nothing is stored: the deferral is the answers themselves, so it lapses on its own. Skips stay out of every count that measures effort or ability (`UserAnswer.attempted`, `Assignment#graded_questions_count` / `#score_percentage`, badges, `DailyPractice`'s median). What the practice screen does with an answer — sound, the feedback card, the side-by-side layout, „Чернова“, „Прочети ми“, the session summary — is in `.claude/rules/practice-screen.md`. Every session is built by `SessionComposer` over `Dispatcher`'s pools; a session that cannot fill even after widening in Fibonacci steps (`Dispatcher::WIDENING_STEPS`) raises `Dispatcher::NotEnoughQuestions`. (The old `AssignmentCreator` module was deleted — it had no production callers, drew from `Question.published` directly and so would have bypassed `practice_pool`'s free-text and deferral rules if ever reconnected.)

Users: `role` enum (student/parent/admin — value 1 was teacher, retired when the role was removed and its users migrated to parent); role decides the landing page (`home_path_for`). Gamification state on users: `total_xp` (events in `xp_events`, level curve in `Levels`), `current_streak`/`longest_streak`/`streak_freezes` (logic in `Streaks`). `current_streak` is only rewritten on the next practice, so every screen — the header pill, the home hero, the profile, the streak badges' progress bars — reads `User#live_streak` (`Streaks.current`, zero once the streak has lapsed); `Streaks.record` and the badge conditions, which run right after a practice, read the column. Per-topic Elo lives in `skills` (user × topic); `users.elo` is the overall rating, updated per answer as its own Elo game against the question — never by adding the per-topic delta, which is measured against the topics' skill average: mixing the two baselines is the drift that once inflated improving students' ratings without bound. Topics form a hierarchy via `parent_id`.

Database: schema format is SQL (`db/structure.sql`). Seeding creates users and the topic tree: `db/seeds/topics.yml` (topics + prerequisite edges) is loaded by `ProblemSeeds.import_topics` via `rake topics:import`, which `db/seeds.rb` calls; `db/seeds.rb` then imports the ladder corpus into an empty bank, so a fresh clone can run a practice session. Questions come from problem files: `rake problems:import FILE=path` takes a file **or a directory of them**. The bank that ships is about 30k questions across four sets, none at `problems.yml` (which `problems:export` overwrites): `db/seeds/ladders/` is the main corpus (25.9k problems in 24 area files, every leaf topic, Elo 600-2800, 14.6k of them interactive across all twenty widgets, 2,035 with a figure, worked step-by-step explanations on all of them); `db/seeds/authored_problems*.yml` are three earlier hand-written batches (~1k); `db/seeds/starter_problems.yml` is a 100-problem dev/demo set; and `db/seeds/arithmetic_facts.yml` is the 7,646 basic arithmetic facts (sums to 100, differences within 100, the 10x10 times table and its division facts), generated from the rule in its header rather than authored. Problem files carry no grade keys; the importer ignores any that older files still have. A problem row is `text`/`topic`/`elo`/`explanation` plus one of `answer` (+ optional `tolerance` for answers rounded with pi), `options` (multiple choice), `widget`, or `rubric`; `image` names a PNG relative to Rails.root and `image_filename` the name it is stored under. Unknown keys are ignored, which is why the ladder files can carry `family` for provenance.

Deployment is a shell script on the box, not Kamal — the `kamal` gem, `config/deploy.yml` and `.kamal/` were removed, because they described an arm64 host, a Docker Hub registry and a `kamal-proxy` that production has never had, and a deploy config that is fiction is worse than none. The real thing: wunderkind.bg is one x86_64 host shared with another app, and `/opt/apps/wunderkind/deploy.sh [branch]` (default `main`; it, the compose file, the `rails` wrapper and Caddy's site file are copied in `ops/`, edit there and install — see `ops/README.md`) fetches from GitHub into `src/`, builds the image and deploys it **blue/green with no downtime**: two slots (`wunderkind-blue`/`-green`, `.live` names the serving one), the shared Caddy lists both and routes only to one whose `/up` answers, and the old slot is drained before it is stopped — `HealthController` answers `/up` down while `tmp/draining` exists, because Thruster passes SIGTERM to Puma but keeps accepting and would 502 everything that arrived during the drain. A release that never gets healthy never takes traffic. Run Rails commands in the live slot with `/opt/apps/wunderkind/rails …` (never `docker exec wunderkind-web`, which no longer exists). **Migrations need no separate step** — `bin/docker-entrypoint` runs `db:prepare` whenever the command is `rails server`, so they apply on boot — but they now run while the old release is still serving, so a migration must not break the code before it. There is no `config/master.key` anywhere: secrets are plain env in `/opt/apps/wunderkind/.env` (`SECRET_KEY_BASE`, `POSTGRES_PASSWORD`, and `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` for duel-invitation pushes — rotating them orphans every subscription), which is why a clone can run the app but cannot decrypt `credentials.yml.enc`. A shared Caddy (`/opt/infra/caddy`) terminates TLS on the `edge` network and 301s www to the bare host — one reason `Seo.origin` is a single string — and a shared Postgres sits on `internal`. `/opt/infra/backup.sh` dumps every database nightly to `/opt/backups`; run it before a migration that rewrites rows. `bin/thrust` still fronts Rails in the image, so the `thruster` gem stays. Errors go to Sentry. Mail goes out through Brevo (`smtp-relay.brevo.com`, credentials in `.env`; the domain is authenticated with Brevo DKIM CNAMEs in Hetzner DNS, where a CNAME value needs its trailing dot or Hetzner appends the zone). The host has two crontab entries, root's: `0 18 * * 0 /opt/apps/wunderkind/rails reports:weekly`, Sundays at 18:00 (the host runs on Europe/Sofia), logging to `/var/log/wunderkind-weekly-report.log`, and `0 10 * * * /opt/apps/wunderkind/rails reminders:children`, daily at 10:00, logging to `/var/log/wunderkind-child-reminder.log`.

## Roadmap context

The product scoping doc (three phases: Foundation → Teachers/Classrooms/Homework → AI/adaptive path) is published as an artifact. All three phases were built (plus live duels, `/challenges`, added after them): Phase 1 (content model v2, gamification core, design system, platform cleanup), Phase 2 (teacher/parent roles, classrooms, homework, daily-minutes mode, email verification/password reset), Phase 3 (adaptive session composer + spaced review + topic mastery, hint ladders, teacher-graded free text, global weekly leaderboard). The teacher side of Phase 2 — the teacher role, classrooms, invites and homework (including the parent-assigned kind), plus the teacher grading of free text — was later removed at the owner's request; parents, managed children and the admin review pipeline stayed. The Claude API integration Phase 3 originally included (hint generation, free-text grading, authoring assistant, review pre-check, budget cap) was removed afterward at the owner's request — questions are generated outside the app; the implementation lives in git history (commits `7d483cf`..`c15e459`) if it's ever wanted back. Mail delivery is configured by environment (see Roles & social) and has been live in production since 2026-10-28, through Brevo; `mailing:grandfather` was run that day.
