# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Wunderkind is a Rails 8 app (Ruby 3.4, PostgreSQL) for math practice: students receive assignments of questions matched to their skill via an Elo rating system, earn XP/levels/streaks/badges, and questions support rich content with math notation and interactive widgets. UI copy is in Bulgarian with full i18n extraction (`config/locales/app.bg.yml` / `app.en.yml`, default locale `:bg`).

## Commands

- `bin/dev` — run the app (foreman: Rails server + `yarn build --watch` for JS + `bin/rails tailwindcss:watch` for CSS)
- `bin/rails db:prepare` / `bin/rails db:seed` — set up the database (seeds create admin@example.com and student@example.com, password `password`)
- `bundle exec rspec` — run tests; single file: `bundle exec rspec spec/services/elo_spec.rb`; single example: append `:LINE`
- `bin/rubocop` — lint (rubocop-rails-omakase); CI runs this plus `bin/brakeman --no-pager` (ignore file: `config/brakeman.ignore`)
- `yarn build` — bundle JS with esbuild into `app/assets/builds` (yarn 4, `nodeLinker: node-modules`)

## Architecture

Core answer flow: `AnswersController#create` delegates to `AnswerSubmission.call` (app/services/answer_submission.rb), which grades the response (`Grading`), updates per-topic skill ratings and the question's Elo (`Elo` module — dynamic K-factor, upset bonuses), awards XP (`Xp`, difficulty-scaled via Elo expected score), records the daily streak (`Streaks`), and awards badges (`Badges` — definitions in code, awards in `badge_awards`). `AnswersController#skip` → `AnswerSubmission.skip` is the "не съм го учил" (I haven't been taught this) path: it records a `user_answers.skipped` row that is neither right nor wrong, leaves the student's rating, XP, streak and badges alone, nudges the question's Elo up by `Elo.skip_adjustment` (an ordinary Elo loss for the question with a small K, so the bump is largest on questions rated at or below the student — the ones plainly mistagged), and defers the topic (`skills.deferred_until`, `AnswerSubmission::DEFERRAL_DAYS`, only for topics with fewer than `DEFERRAL_MAX_GAMES` games). Skips stay out of every count that measures effort or ability (`UserAnswer.attempted`, `Assignment#graded_questions_count` / `#score_percentage`, badges, `DailyPractice`'s median). `AssignmentCreator` builds assignments from published questions at the dispatcher's target difficulty, widening in Fibonacci steps; supports a `topics:` filter.

Content model: `Question#body` is a restricted ProseMirror-style JSON document (paragraph/text/bold/italic/math/hardBreak) rendered server-side by `RichContent` (KaTeX renders math client-side via the `math` Stimulus controller); `body_text` is the plain-text projection. `answer_type` enum: `multiple_choice` (options in `possible_answers` with a `correct` flag), `exact_value` (graded by `ExactValue` — fractions/decimals/percent/BG-comma equivalence, tolerance), `interactive` (widget state graded server-side by the `Widgets` registry — the solution never reaches the client). Twelve widgets ship: `number_line`, `angle_dial`, `clock_hands` and `coordinate_plot` place a value; `ordering`, `categorize` and `matcher` arrange; `multi_select` chooses; `blanks` and `grid_fill` fill in; `fraction_bars` and `grid_shade` shade. Each is a checker plus display in `app/services/widgets.rb` (plus a `solution_display` where the stored solution isn't shaped like a finished state — `multi_select` keys it `correct` rather than `selected`, and a counted `grid_shade` names no cells at all, so both would otherwise show an empty „верен отговор“ chip), a Stimulus controller in `app/javascript/controllers/widgets/`, a partial in `app/views/widgets/`, a hint string in the locales and a demo on `/design-system`. The authoring form can only build `QuestionFormParams::EDITABLE_WIDGETS` (number line, ordering, fraction bars); a question using any other widget keeps its stored grading when edited there, because those parameters are generated with the problem rather than typed, `free_text` (reserved, Phase 3 AI grading). `grading` jsonb holds expected value/widget params+solution. `status` enum: draft/private_library/in_review/published — only published questions enter practice. A question can carry one image on its polymorphic `attachable` (`QuestionImage`, an Active Storage attachment shown above the body in the practice, duel and preview views). Legacy `text`/`answer` columns remain nullable until grading parity is confirmed in production, then drop.

Students report broken questions: `question_reports` (question × user, `reason` enum — misleading / wrong_answer / missing_answer / typo / image / broken / other — plus an optional note, `status` open/resolved/dismissed and who closed it). The control is `shared/_report_problem`, a folded-away `<details>` under the answer controls on the practice screen (in both states — a wrong accepted answer is usually only discovered *after* answering) and on the review of a past answer; `QuestionReportsController#create` files it through `QuestionReport.file!`. Like a skip it is not an answer, and unlike a skip it is not even a measurement: reporting grades nothing, moves no Elo, XP, streak or `skills` row, and leaves the question answerable — the only consequence is a row in the admin queue, because the fix is always a human editing the question. A unique index on (question, user) means re-reporting rewrites the student's own row and reopens it rather than stacking duplicates, so the student sees what they said instead of a second form. `Overseer::QuestionReportsController` is keyed by *question*, not by report (`QuestionReport.open_questions`, newest complaint first): several students flagging one problem is one thing to read and one edit to make, so every action closes the whole pile — „Готово“ (resolved), „Няма проблем“ (dismissed) or „Скрий задачата“, which drops the question back to `draft`, the one status no practice session, homework or duel draws from. The open count rides in the admin nav label, and the questions list flags reported rows. Duels report too, through `ChallengeReportsController` (`POST /challenges/:id/reports`) into the same rows and the same queue — reporting is not in the class of things a duel withholds (a hint and a skip would both be worth points to whoever used them fastest; a report awards nothing, skips nothing and stops nothing, so it costs the reporter their own seconds and nobody else's, which `reports.clock_note` says out loud). Mid-match the control sits under the answer controls on the problem in front of the player and comes back to it — re-serving does not re-stamp `question_started_at`, so the report buys no thinking time; on the result screen, the one place the whole match is listed with its answers, `challenges/_report` is a single control with a picker over the five problems (already-reported ones marked ⚑) rather than a flag on each row of a scoreboard. `shared/_report_reasons` is the shared body of every report form, so a duel and a practice question ask the same question in the same words.

Student home (`/calendar`, `CalendarsController#show`) is a hero CTA → duel card → homework → history, with a right rail of level ring / rating band / next badge. The month grid of `aspect-square` cells is gone (with it the `Calendar` service and the `shared/svg` partials): history is a nine-week contribution strip built by `PracticeHistory`, whose active days still link to that day's sessions. `RatingBand` names Elo ranges (Начинаещ/Уверен/Силен/Отличен/Състезател, the 1400 boundary shared with topic mastery) so a raw rating never leads on a student-facing screen. `Badges::Badge#progress` is an optional lambda over `Badges.stats_for(user)`, set only on countable badges, which drives the per-badge bars and `Badges.next_to_unlock`. `math_value`/`shared/_frac` (and `app/javascript/lib/frac.js` for the widgets) set a bare "3/4" as a stacked fraction so widget maths matches the typeset question body.

Users: `role` enum (student/teacher/parent/admin); role decides the landing page (`home_path_for`). Gamification state on users: `total_xp` (events in `xp_events`, level curve in `Levels`), `current_streak`/`longest_streak`/`streak_freezes` (logic in `Streaks`). Per-topic Elo lives in `skills` (user × topic); `users.elo` is the overall rating, updated per answer as its own Elo game against the question — never by adding the per-topic delta, which is measured against the topics' skill average: mixing the two baselines is the drift that once inflated improving students' ratings without bound. Topics form a hierarchy via `parent_id`.

**There are no school grades anywhere in the model** — a first-grader who can do third-grade work gets it, and a fifth-grader who can't doesn't. `users.grade` and `questions.grade_min`/`grade_max` were dropped; difficulty is the question's Elo and ability is the student's, full stop.

Adaptivity (no AI/LLM integration — it was built and then removed by decision; question content is generated outside the app): `Dispatcher` (app/services/dispatcher.rb) is the single answer to "which problems suit this student right now" — it owns the pools (`practice_pool`, and `available_pool`, which drops topics the student has deferred by skipping), the difficulty target (`TARGET_SUCCESS_RATE` inverted through the Elo expectation, so the aim sits ~147 points below the student), the cold start (`starting_rating` = the 10th percentile of the published bank, applied by `User.new_student`; starting low is the cheap mistake), and calibration (`calibrating?` until `CALIBRATION_ANSWERS` attempted answers; `calibration_rungs` / `at_rung` build a ladder climbing `CALIBRATION_CLIMB` above the student). `SessionComposer` owns the *mix*, not the difficulty: a calibrating student gets `calibration_questions` (the ladder rotated across unlocked topics, so the curriculum graph still holds), everyone else gets spaced review due topics + frontier topics unlocked by `topic_prerequisites` + one stretch question + filler at the dispatcher's target. Two variety guards run there: `MAX_PER_TOPIC` spreads the frontier across topics, and `MAX_PER_SHAPE` (with the `diversify` pass, which recognises a template via `ProblemSeeds.shape_of`, mirrored in SQL as `SHAPE_SQL`) caps problems sharing one template — without it the arithmetic fact tables, being thousands of `a + b` rows in one topic, fill every young session; the cap yields rather than let a session shrink. `AnswerSubmission` schedules spaced review (SM-2-ish intervals on `skills`), detects topic mastery (rating ≥ 1400, ≥ 10 games → `mastered_at`, XP bonus), and halves XP for hinted correct answers. Hint ladders live in `question_hints` (a `ladder` of strings, revealed one rung per click by `hints_controller.js`, `hints_used` halving the XP of a correct answer). Two ways in: typed at `/overseer/questions/:id/hint`, where `reviewed_at` gates them because a human is mid-edit, or shipped in a problem file's `hints:` key, which arrives reviewed — the answers and explanations beside them go live on import too, and 22.6k ladders were never going to be typed in one at a time. Families emit them with `c.q(hints: [...])`; `check.rb` refuses a rung that contains the answer, and 56 families (the puzzle, kangaroo and deduction ladders — 3.2k problems) carry one so far. **A hint is not a shortened explanation**: an explanation is read after a wrong answer and states the answer, a hint is read instead of giving up and must not. Availability is the *session's* choice, not the question's: `Assignment#hints_allowed?` reads the nullable `assignments.hints_allowed` if set, else the teacher's `homeworks.hints_allowed` when the session belongs to a homework, else `Assignment::HINTS_BY_KIND` (practice and daily yes, homework no). Duels never reach it — they have no assignment, and a hint would be worth points to whoever used it fastest. Free-text answers always record `verdict: pending_review` (`UserAnswer#pending_review?`, which the student-facing views treat as a fourth outcome beside right/wrong/skipped rather than as wrong); the homework assigner grades them via `AnswerOverridesController`. The global weekly leaderboard (`/leaderboard`) is nickname-only, Sofia-time Monday reset.

Challenges (live duels): `/challenges` pairs two students head-to-head on the same problems with one shared clock, scored on speed as well as correctness. `ChallengeMatchmaker` *is* the queue — an unmatched player is a `waiting` `Challenge` with one `challenge_participants` row, and the next player to press the button joins the closest lobby (within `MAX_GAP` rating points, or anyone who has waited past `PATIENCE`) and starts the match under a row lock; lobbies nobody joined inside `Challenge::LOBBY_TTL` are written off lazily, on the next matchmaking run or on the waiting player's own next poll. The problems come from `Dispatcher.pick_shared`, which aims at the midpoint of the two ratings and drops topics either player has deferred. `ChallengeScoring` pays `CORRECT_POINTS` for a correct answer plus up to `SPEED_POINTS` scaled by how much of the per-problem window was left, so a fast wrong answer is worth nothing and two correct answers always beat one. Durations are measured server-side from `challenge_participants.question_started_at` (stamped when a problem is served, cleared on answer), so the speed bonus can be neither forged by the client nor reset by reloading. `ChallengeSubmission` grades through `Grading`, pays XP per answer and records the daily streak, then finalizes when both players are done or the clock runs out — points decide it, a points tie goes to the lower total time, a tie on both (or a match nobody scored in) is a draw — awarding `Xp::CHALLENGE_WIN_BONUS`/`CHALLENGE_DRAW_BONUS`/`CHALLENGE_PLAY_BONUS` and the `duel_win`/`duel_wins_10` badges. A duel deliberately touches **no** measurement: no per-topic skill update, no question Elo, no `user_answers` row, so calibration and the dispatcher never read answers given under race conditions as evidence about a student. `ChallengeRecord` is a pure query over finished matches. The screens are driven by `challenge_controller.js` polling `GET /challenges/:id/state` (the app has no ActionCable setup); the server is the only authority on the clock, the scores and when a match ends, and opponents are shown by nickname only, like the leaderboard. Duels have no hints and no "не съм го учил" — both would be worth points to whoever used them fastest.

The landing page (`StaticPagesController#landingpage`, the `root`) is the one screen a visitor sees. Its artwork *is* the product: a real `.practice-card` with `.choice-button`s and a real `.fb-band` inside a `.landing-peek` frame, the student's own `shared/_rating_band_card`, and duel chrome — no illustrations and no stock photography, and amber appears in exactly one place, inside the screenshot, where it still means "you earned something". Every figure on the page is read off the constant that implements it (`Challenge::SECONDS_PER_QUESTION`, `ChallengeScoring::CORRECT_POINTS`/`SPEED_POINTS`, `DailyPractice::DEFAULT_MINUTES`, `Dispatcher::CALIBRATION_ANSWERS`/`TARGET_SUCCESS_RATE`, `AnswerSubmission::DEFERRAL_DAYS`, `RatingBand::BANDS`, `Widgets::REGISTRY`) so a claim cannot drift away from the code; the only query is the published-bank count, cached for a day, floored to a round hundred and swapped for the daily-minutes tile when the bank is too small to quote. There is no pricing, no usage metric and no testimonial, because none of the three exist yet. The `.landing-*` primitives and `.button-hero` are documented at `/design-system` under „Публична страница“.

Roles & social: teachers own `classrooms` (students join by `invite_code`; `Teachers::` namespace, application layout); parents link to children via `parent_links` (`users.link_code`, shown on the student profile; `Parents::` namespace), and a child too young for an email gets a **managed account**: `User.create_managed_child!` makes a student with no email (`users.email` is nullable, presence required only `unless: :managed?`), a random unused password and `users.managed_by_id` pointing at the parent, plus the usual `parent_links` row. Such an account has no login of its own — it is reached by switching profiles (see Controllers). Creating a child with an email *and* password still works and is also managed, so the parent can switch in; a child linked by code is not managed and cannot be switched into, and an emailless child cannot be unmanaged (nobody would be able to reach them). `HomeworkCreator` builds a `Homework` (+`homework_questions`) and materializes one resumable `kind: :homework` assignment per student — hand-picked from the assigner's library/published pool plus auto-fill near the group's Elo; results matrix via `Homework#completion_for`. `DailyPractice` sizes a `kind: :daily` session from `daily_minutes_target` and the student's median answer time. `Leaderboards.weekly_xp` is a pure query over `xp_events` (classroom boards, teacher-toggleable). Teacher questions are private by default; `submit_for_review` → admin queue at `Overseer::ReviewsController`. Email verification (`users.verified_at`, `generates_token_for`) gates teacher/parent mutations (`require_verified_email`); password reset via `PasswordResetsController`; mail through `UserMailer`.

Controllers: `AuthenticatedController` is the base for logged-in pages (session auth, `current_user` from `session[:user_id]`); auth endpoints are rate-limited. The session carries two identities: `signed_in_user` is whoever typed the password and `session[:child_id]` is the managed child whose profile is open, so `current_user` — what every other line of the app reads — is the child while a profile is open, and the practice, rating, XP and streak all land on the child. `ChildSessionsController` (`POST /switch-child/:id`, `DELETE /switch-child`) is the only way in and out; it re-checks `signed_in_user.managed_children` on *every* request rather than trusting the switch, `reset_session` on sign-in and sign-out drops any open profile, and while one is open the parent's own area is closed (`current_user` is a student) with `shared/_child_session_bar` in the `application` layout the only seam and the way back — it also lists the login's other managed profiles (`other_child_profiles`), because a household passes one device around and switching child should be one tap rather than a trip through the parent's own screens. `Overseer::` is the admin area (`Overseer::BaseController` requires `current_user.admin?`, `admin` layout). Layouts: `application` (sticky nav, plus a `shared/_tabbar` bottom nav for students at phone widths), `modal` (answer flow), `landingpage` (the public marketing shell: header with Вход + Създай профил and section anchors, no app nav and no reward pills, plus the footer), `simple` (auth), all sharing `shared/_head`. The `modal` layout has two shapes: a page that sets `content_for :bare` owns all of its own chrome and gets a full-bleed gray page (the practice flow and duels, which supply `shared/_practice_header` or `challenges/_scoreboard`); anything else keeps the original white dialog with the back/close row. `back_path`/`close_path` params must pass through the `internal_path` helper (XSS guard).

Frontend: Turbo + Stimulus (controllers in `app/javascript/controllers`, registered in `index.js`), esbuild, Tailwind v4 (design tokens in `@theme` in `app/assets/tailwind/application.css`; every component rule lives in `@layer components` so a utility in the markup wins over what the component `@apply`s — unlayered rules outrank all utilities and used to silently beat them). Note esbuild's entry glob is `app/javascript/*.*`, so shared JS helpers go in a subdirectory (`app/javascript/lib/`) or they become their own bundle. Authoring uses Tiptap with a custom inline `math` node (KaTeX-rendered, MathLive popover editing) in `editor_controller.js`; students type exact-value answers via MathLive (`math_input_controller.js`, fonts in `public/mathlive-fonts`). KaTeX CSS/fonts are vendored in `app/assets/stylesheets`. The design system lives at `/design-system` (open in development, admin-only in production). No system tests are generated for this app.

Database: schema format is SQL (`db/structure.sql`). Seeding creates users and the topic tree: `db/seeds/topics.yml` (topics + prerequisite edges) is loaded by `ProblemSeeds.import_topics` via `rake topics:import`, which `db/seeds.rb` calls; `db/seeds.rb` then imports the ladder corpus into an empty bank, so a fresh clone can run a practice session. Questions come from problem files: `rake problems:import FILE=path` takes a file **or a directory of them**. The bank that ships is about 30k questions across four sets, none at `problems.yml` (which `problems:export` overwrites): `db/seeds/ladders/` is the main corpus (22.9k problems in 21 area files, every leaf topic, Elo 600-2800, 12.8k of them interactive across all twelve widgets, 1,203 with a figure, worked step-by-step explanations on all of them); `db/seeds/authored_problems*.yml` are three earlier hand-written batches (~1k); `db/seeds/starter_problems.yml` is a 100-problem dev/demo set; and `db/seeds/arithmetic_facts.yml` is the 7,646 basic arithmetic facts (sums to 100, differences within 100, the 10x10 times table and its division facts), generated from the rule in its header rather than authored. Problem files carry no grade keys; the importer ignores any that older files still have. A problem row is `text`/`topic`/`elo`/`explanation` plus one of `answer` (+ optional `tolerance` for answers rounded with pi), `options` (multiple choice), `widget`, or `rubric`; `image` names a PNG relative to Rails.root and `image_filename` the name it is stored under. Unknown keys are ignored, which is why the ladder files can carry `family` for provenance.

The ladder corpus is built by `tools/authoring` (see its `README.md` for the commands and `PROBLEM_TYPES.md` for the catalogue of problem types and the recipe for adding more of each), which runs outside Rails: the app still has no question generator in it and never makes a question at runtime. A *family* there is one type of problem written at six rising Elo ratings with a few variants each, so a student who cannot do a type meets the same type lower down and climbs back up as their rating recovers — `spec/services/ladder_corpus_spec.rb` guards that property, along with answer parseability, figure files and explanation depth. Rebuild with `ruby tools/authoring/build.rb`, then `tools/authoring/rasterize.sh` (headless Chrome turns the figure SVGs into PNGs — Active Storage will not serve SVG inline), then `ruby tools/authoring/check.rb`, which validates answer parseability, widget shapes (values on the step grid, points inside the plane, bins that are not empty), figure files and explanation depth. Figures are drawn to scale from the numbers in the question, and every number in a figure is repeated in the text because the views render question images with an empty `alt`.

Note that `problems:export` thins to `MAX_PER_SHAPE` per template and drops images and `family`, so an export is not a backup of the fact tables or the ladder corpus — re-import the files instead. `rake problems:export` writes the database back out (problems to `db/seeds/problems.yml`, the topic tree to `topics.yml`). `rake problems:stats` reports the distribution. The earlier parametric generator was removed for producing near-duplicates; the ladder builder answers that with families whose variants are capped per rung and deduplicated against the whole corpus and the existing bank.

Deployment is via Kamal (`config/deploy.yml`) to wunderkind.bg; errors go to Sentry.

## Roadmap context

The product scoping doc (three phases: Foundation → Teachers/Classrooms/Homework → AI/adaptive path) is published as an artifact. All three phases are built (plus live duels, `/challenges`, added after them): Phase 1 (content model v2, gamification core, design system, platform cleanup), Phase 2 (teacher/parent roles, classrooms, homework, daily-minutes mode, email verification/password reset), Phase 3 (adaptive session composer + spaced review + topic mastery, hint ladders, teacher-graded free text, global weekly leaderboard). The Claude API integration Phase 3 originally included (hint generation, free-text grading, authoring assistant, review pre-check, budget cap) was removed afterward at the owner's request — questions are generated outside the app; the implementation lives in git history (commits `7d483cf`..`c15e459`) if it's ever wanted back. Not configured in production yet: SMTP delivery (verification/reset emails only log in development).
