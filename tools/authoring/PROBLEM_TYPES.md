# Problem types in the bank, and how to make more of each

This is the working reference for the shipped question corpus: what kinds of
problem exist, what each kind is *for*, and the recipe for adding more of it.

The corpus lives in `db/seeds/ladders/*.yml` and is generated by
`tools/authoring` (see `README.md` for the build commands). Today it holds
**22,897 problems in 530 families**, Elo 600–2800:

| answer format | problems | what it is good for |
|---|---|---|
| interactive widget | 12,756 | anything the student can *do*: place, shade, sort, fill, match |
| typed exact value | 9,303 | one number, checked with `ExactValue` (fractions ≡ decimals ≡ percents) |
| multiple choice | 838 | symbolic or verbal answers a typed field cannot compare |
| with a figure | 1,203 | geometry, charts, number lines, solids — drawn to scale from the numbers |

§3–§5 catalogue the problem *types* and §10 lists every family there is, area by
area — that one is the index to read before writing a new family.

A §5 section may describe a type that is **written but not generated**: the
family and its solver exist, the corpus does not hold its problems yet, and
building it is a deliberate step. Such a section says so in its first line, and
the counts above — which are the corpus files, not the families in the tool —
leave it out.

## 1. The unit of authoring is a *family*, not a problem

A family is one **type** of problem, written once, at six or seven rising Elo
ratings, with several variants per rung:

```ruby
Authoring.family "pct.of_amount", topic: "Проценти", area: "fractions",
                 rungs: [ 970, 1060, 1150, 1240, 1330, 1430 ], variants: 6 do |c|
  pct  = c.pick(c.by_level([ [ 10, 50 ], [ 10, 20, 25, 50 ], ... ]))   # difficulty
  base = c.int(c.by_level([ 2..12, 2..20, 4..40, ... ]))               # rises per rung
  c.q(text: "...", answer: Num.ans(base * pct / 100), explanation: Explain.build(...))
end
```

Everything else in this document is a catalogue of what can go in the block.

**Rung rules** (enforced by `spec/services/ladder_corpus_spec.rb`):
at least 4 rungs, at least 300 points from bottom to top, never more than 150
points between neighbours, and no empty rung. Close rungs are the point: a
student who fails a type drifts *down that type's ladder* rather than out of it.

## 2. Answer formats and when to use which

| format | use it when | how to write it |
|---|---|---|
| `answer:` | the answer is a single number | `answer: Num.ans(value)` — ASCII minus, comma decimals, fractions as `3/4` |
| `answer:` + `tolerance:` | the answer is rounded (anything with π) | `tolerance: "0.05"` |
| `options:` | the answer is symbolic (`(x+3)(x−2)`), verbal (`да`/`не`), or a formula | 3–4 options, distractors = real mistakes |
| `widget:` | the student should *act*, not type | see the catalogue below |
| `figure:` | a diagram carries part of the information | `Figures.*`, and repeat every number in the text |

Rule of thumb: **numeric → typed, symbolic → options, procedural → widget.**
A typed field compares strings when it cannot parse a number, so `x = 3` or
`2√3` typed by hand will be marked wrong. Never ask for those.

## 3. The interactive catalogue (12 widgets)

Each widget is `WidgetKit.<builder>` in the authoring tool, a checker in
`app/services/widgets.rb`, and a Stimulus controller under
`app/javascript/controllers/widgets/`. Counts are problems currently shipping.

### 3.1 `blanks` — one or more numbered boxes (3,865)
For answers that have **two halves**: both roots, x and y, quotient and
remainder, perimeter and area, НОД and НОК, period and last digit.

```ruby
widget: WidgetKit.blanks([ [ "q", "частно", quotient ], [ "r", "остатък", rest ] ],
                         prompt: "#{dividend} : #{divisor}")
```
*More of it*: any procedure whose method has two outputs. Each field is graded
with `ExactValue`, so `1/2` and `0,5` both pass; pass `tolerance:` for rounded
values. Do not use it for one number — that is a typed answer.

### 3.2 `multi_select` — choose every option that fits (2,059)
For properties that must be judged option by option: divisibility, primality,
equivalent fractions, valid triples, true statements, losing positions.

```ruby
widget: WidgetKit.multi_select([ [ "34", false ], [ "45", true ], [ "51", true ], [ "62", false ] ])
```
*More of it*: pick a property, generate 2–3 numbers that have it and 3 near
misses. **The stem must list the options** (`"Кои от числата 34, 45, 51, 62 ..."`)
— the importer keys questions by their text, so a fixed stem collapses the whole
family into one problem.

### 3.3 `grid_fill` — a table with holes (1,076)
Magic squares, Latin squares, times tables, function machines, place-value
tables, two-way frequency tables, column addition, cross-number puzzles.

```ruby
widget: WidgetKit.grid_fill(rows: [ [ 8, nil, 6 ], [ nil, 5, nil ] ], answers: [ [ 8, 1, 6 ], [ 3, 5, 7 ] ],
                            column_headers: %w[…], row_headers: %w[…])
```
*More of it*: any structure with a **checkable constraint** — rows summing to a
constant, each symbol once per row, a rule linking input to output. Keep grids
at most 5×5 and blanks at most ~8, or the widget stops being a maths exercise.

### 3.4 `categorize` — items into named groups (1,124)
Prime/composite, even/odd, terminating/repeating decimals, acute/obtuse,
possible/impossible, growing/shrinking, winning/losing.

```ruby
widget: WidgetKit.categorize(bins: [ [ "p", "просто" ], [ "c", "съставно" ] ],
                             items: [ [ "i1", "17", "p" ], [ "i2", "21", "c" ], … ])
```
*More of it*: any binary or ternary classification whose rule is worth stating.
Every bin must get at least one item, and the stem must name the items.

### 3.5 `matcher` — pair the two columns (1,021)
Fraction ↔ percent, expression ↔ value, shape ↔ formula, equation ↔ root,
number ↔ binary, event ↔ probability, action ↔ inverse action.

```ruby
widget: WidgetKit.matcher([ [ "1/4", "25%" ], [ "1/2", "50%" ], [ "3/4", "75%" ] ])
```
*More of it*: any one-to-one correspondence with 3 pairs. Labels must be
distinct on both sides, or two answers become right at once.

### 3.6 `coordinate_plot` — click lattice points (835)
Plot a point, complete a rectangle, reflect/translate, mark the midpoint, plot
the intercepts, plot the solution of a system, plot a data point.

```ruby
widget: WidgetKit.plot(points: [ [ 2, 1 ] ], fixed: [ [ -3, 2, "A" ] ], x_range: (-5..5), y_range: (-5..5))
```
*More of it*: anything whose answer is a **position**. The order of placement
never matters; keep every solution point inside the range and off the given
points.

### 3.7 `grid_shade` — colour cells on squared paper (849)
Two modes. *Exact set*: complete a symmetry, mark a knight's moves, shade one
colour class of a chessboard. *Count only*: shade 3/8 of the grid, shade a
figure with area 12, shade 40%.

```ruby
widget: WidgetKit.grid_shade(rows: 4, cols: 8, cells: [ "0,1", "1,2" ])   # exact
widget: WidgetKit.grid_shade(rows: 4, cols: 10, count: 12, given: [ "0,0" ]) # any twelve
```
*More of it*: area and fraction models at the bottom of the ladder; tilings,
parity and colouring arguments at the top.

### 3.8 `ordering` — arrange in sequence (588)
Numbers, negatives, decimals, fractions, mixed notations, powers, measures,
probabilities, steps of a solution, figures by area.

*More of it*: any set with a total order; 3–5 items. Include the items in the
stem for uniqueness.

### 3.9 `number_line` — place a point (459)
Integers, negatives, decimals, fractions, the result of an operation, a rounded
value, the midpoint, a percentage of 100.

*Constraint*: `(max − min) / step ≤ 40` and the answer must sit **on** the step
grid, or the student cannot place it. `check.rb` enforces both.

### 3.10 `clock_hands` — set the time (387)
Read/set a time, elapsed time forwards and backwards, half hours, arithmetic
modulo 12.

### 3.11 `angle_dial` — turn a ray (299)
Set an angle, its complement or supplement, the third angle of a triangle, an
exterior angle, a polygon's interior angle, the angle between clock hands.

*Constraint*: the answer must be a multiple of the dial's step (5° by default;
use `step: 1, tolerance: 2` for angles like 108°).

### 3.12 `fraction_bars` — shade parts of a strip (194)
The first fraction model: shade 3/4, an equivalent fraction, a percentage, a
decimal, the remainder, a sum of like fractions.

## 4. The written-answer catalogue

The typed families (`arithmetic`, `numbers`, `fractions`, `geometry`, `logic`,
`word_problems`, `algebra`, `functions`, `advanced`): one number as the answer,
graded by `ExactValue`. Nothing to click, which is the point — a student who can
only answer when a widget offers the moves has not learnt the arithmetic.

### 4.1 Bare computation — „Пресметни: 16 + 21.“

An expression and nothing else, the plainest problem in the bank. It earns its
place twice over: a student who cannot add two two-digit numbers cannot do
anything above it, and this is the one type whose difficulty is honestly just
the size of the numbers and whether the digits cross a ten.

| type | family | rungs | what rises |
|---|---|---|---|
| sum | `add.column_carry` | 690–1070 | 11–44 with no carry → 15–79 carrying → three digits → four |
| difference | `sub.column_borrow` | 700–1090 | 25–69 no borrow → 22–95 borrowing → three digits → four |
| product, one-digit multiplier | `mul.long_single` | 780–1220 | 12–40 · 2–4 → 23–99 · 3–6 → 2500–9800 · 6–9 |
| product, two-digit multiplier | `mul.long_double` | 900–1340 | 11–25 · 11–19 → 210–980 · 21–75 |
| quotient | `div.long` | 820–1270 | dividends to ~100, divisor 2–9 → dividends to ~29 000, divisor 12–32 |
| missing addend / factor | `add.missing_number`, `div.missing_factor` | 700–1220 | `1 + ☐ = 6` → the same with three- and four-digit numbers |
| several operators | `order.two_ops`, `order.brackets`, `order.four_ops`, `order.powers`, `order.with_negatives` | 850–1560 | one operator → brackets → four operators → powers → negatives |

36 problems each (6 rungs × 6 variants), all in `families/arithmetic.rb`.
**Up to 100** — the band the youngest
students live in — is the bottom rung of each of those (`11–44 + 11–44`,
`25–69 − 25–69`, `12–40 · 2–4`, `~100 : 2–9`) plus, in bulk, the fact tables in
§4.2. Above it the same families keep going: the type does not change when the
numbers get longer, which is exactly what makes it a ladder.

Three rules that belong to this type in particular:

* **`check.rb` computes the stem.** A question of the form `Пресметни: <израз>.`
  is parsed, evaluated and compared with the stated answer — the one place where
  the tool checks the *mathematics* and not just the shape. It works while the
  expression is digits and `+ − · : ² ³ ( )`, so keeping the typography (`·` for
  multiplication, `:` for division, U+2212 for minus) keeps the check.
* **Force the draw to be the type.** `add.column_carry` rejects a pair that does
  not carry on a carrying rung *and* a pair that does on the rung below it;
  `sub.column_borrow` does the same for borrowing. Without that the rung is a
  lottery and half of it teaches the wrong lesson.
* **The explanation is the written algorithm**, digit by digit, with the carry
  named ("пишем 5, наум 1") and a `check:` line that inverts the operation
  (`сборът − второто събираемо`, `частното · делителя`). That is what the
  student who got it wrong needs, and it is why these families sit *next to* the
  fact tables rather than being replaced by them.

### 4.2 The fact tables — drill, generated from a rule

`db/seeds/arithmetic_facts.yml`, outside the ladder corpus and not counted in
the totals at the top of this file: 7,646 statements of the form „Колко е 7 + 8?“,
Elo 663–920, generated from the rule in the file's own header rather than
authored, and carrying **no explanation** — a wrong answer to 7 + 8 needs
practice, not prose.

| table | rows | the rule |
|---|---|---|
| sums to 100 | 2,500 | `a + b ≤ 100`, `1 ≤ a ≤ b` — each commutative pair once |
| differences within 100 | 4,948 | `a − b`, `1 ≤ b < a ≤ 100` |
| the 10×10 times table | 99 | both orders |
| its division facts | 99 | `(b·q) : b`, `b, q ≤ 10` |

They are not families because they are not ladders: a family is one type written
at rising ratings, a fact table is a whole finite set inside one band. Being one
template each, they are also what `SessionComposer::MAX_PER_SHAPE` (= 2) exists
for — without that cap thousands of `Колко е # + #?` rows in a single topic fill
every young session — and what makes `problems:export` a lossy copy of them
(`ProblemSeeds::MAX_PER_SHAPE` = 5 per template, so re-import the file instead).

*More of it*: extend the rule in the header and regenerate; never hand-add rows.
The gaps, in the order they matter:

1. **Multiplication and division within 100 are thin** — 198 statements against
   7,448 for addition and subtraction. The table stops at 10×10 and the division
   facts are its exact inverse, so a child drilling multiplication meets a
   twentieth of the material a child drilling addition does.
2. **Division with a remainder** as drill (`53 : 6`): every division fact in the
   file divides exactly. The *type* is covered in the ladder — `rem.basic` (36),
   `blank.division_remainder` (66, quotient and remainder in two boxes, §3.1),
   `div.share_remainder` (36, as a story) — so what is missing is only the finite
   table of `a : b` with a remainder within 100, if drill is what is wanted.
3. **The mental-arithmetic moves**: complements (`☐ + 37 = 100`), doubles and
   halves, ±10 and ±100 — each a finite set with an obvious rule. (×10 and ×100
   exist as a ladder family, `mul.powers_of_ten`, but not as a table.)
4. The times table to 12×12.

Two constraints on all of it. The stem must carry its numbers, because the
importer keys questions by their text. And the existing multiplication rows say
`×` where the rest of the corpus says `·`: regenerating with the right sign
writes *new* questions and orphans the old ones, so that is a migration to
decide on, not a rebuild to run.

### 4.3 Type groups worth knowing

* **Written algorithms** — column addition/subtraction/multiplication/division,
  with the carry or borrow spelled out in the explanation.
* **Context problems** — shopping, sharing, saving, tickets, recipes, reading.
  Names, goods and containers come from `Props`; keep verbs gender-neutral
  (aorist, no participles), and avoid possessive pronouns.
* **Reverse problems** — from part to whole, from area to side, from sum to
  addend. These are the rungs that catch students who only know the forward move.
* **Two-step problems** — "of the remainder", successive discounts, buy-then-share.
* **Formula work** — perimeter/area/volume, Pythagoras, similarity, circle,
  progressions, derivatives.
* **Classification and comparison** — which is bigger, which fits the rule.
* **Estimation** — round, then compute; the explanation must say how far off it is.

## 5b. Types taken from competition papers

These came from problems pasted in one at a time and generalised into ladders.
Two of them need a **solver**, not just a formula: the builder enumerates every
candidate and keeps the problem only if the answer is forced. That is the rule
for any deduction type — a puzzle with two answers is not a puzzle.

| type | widget | family | how the builder guarantees it |
|---|---|---|---|
| who-is-who from a fixed tally ("three solved 3, two solved 2") | multi_select, categorize, blanks | `deduce.minority_group`, `deduce.assign_all`, `deduce.two_people` | enumerates all assignments of the tally, keeps the ones where exactly one satisfies the clues; the explanation is produced by *deducing*, and a puzzle whose derivation the narrator cannot finish is dropped |
| circular seating, forced neighbours | multi_select | `logic.circle_neighbours` | enumerates all seatings (rotations collapsed, reflections kept — the clues say clockwise); asks only about a person whose neighbours are the same in every surviving seating, and only about someone the adjacency clues do not name |
| two kinds of creature, two attribute totals | blanks | `logic.two_creatures` | searches for other non-negative integer solutions and rejects the problem if one exists |
| extremal share ("each ate at least 2 — how many could one eat?") | blanks | `logic.extremal_share` | asks for the others' minimum *and* the maximum, so the method is visible |
| digit product and the zero trap | blanks, multi_select | `digits.sum_and_product`, `digits.zero_product_pick` | zeros get commoner up the ladder; the `watch` line changes depending on whether this variant contains one |
| counting under digit constraints | blanks | `count.digit_choices` | asks for both factors and the product — the multiplication principle made explicit |
| Latin square drawn with ladybugs, one line of it asked | figure + blanks | `puzzle.ladybug_square` | enumerates every Latin square consistent with the clues and keeps the problem only if the asked cells hold the same ladybug in all of them — the grid itself may still have several completions, because it is the *question* that has to have one answer; then re-derives the answer by row/column elimination aimed at the asked cells, and drops the problem if that narration cannot finish, so the explanation is the chain the builder actually walked. Difficulty is the length of that chain — how many cells outside the asked line have to be filled first — not the size of the grid, which stops at 4x4 |
| arithmetic on pictures (lines, not parts) | figure + typed | `fig.square_line_equation` | the explanation contrasts counting lines with counting parts, which is where the trap is |
| row with a neighbour condition ("each child stands between a girl and a boy") | blanks, grid_shade, multi_select | `logic.row_between`, `shade.row_between`, `pick.row_possible` | the condition is on a child's *neighbours*, so positions two apart alternate and the row splits into two chains; even lengths give one row, n ≡ 1 (mod 4) forces the count but not the row, n ≡ 3 (mod 4) is impossible — one problem, three rungs of reasoning |
| age with a time shift | blanks | `logic.age_shift`, `logic.age_sum_shift` | going back to the present *before* using the sum; the second family isolates the trap that a sum of k ages grows by k·years |
| most items within a budget | blanks, multi_select | `logic.max_items_budget`, `pick.affordable_sets` | greedy from the cheapest, with the leftover money asked for so the method shows |
| exact payment from given coins | multi_select | `pick.exact_payment` | subset sums of the coin multiset; coin sets are chosen without a 1 so some amounts are genuinely unreachable |

**Clue kinds available to the deduction builder**: direct ("X solved 3"),
negative ("X did not solve 3"), comparison ("X solved more than Y"), equality
("X and Y solved the same"), difference ("X and Y solved different amounts"),
and for circles "X stands immediately after Y" and "X and Y are not neighbours".
Clues may share people — forbidding that makes whole configurations impossible.

## 5c. Path counting on a staircase (Кенгуру №26)

The type: a figure made of unit squares, left aligned, never narrowing
downwards. The kangaroo sits in the top-left square **А**, its mother in the
bottom-right square **Б**, and it moves from square to square *only right and
down*. How many different paths are there? (The plain rectangle, typed and
without a figure, was already in the bank as `count.grid_paths` in `logic`,
§10.19 — a new path-counting family belongs beside one of the two, not next to
both.) It is the cheapest problem in the
corpus that needs a table rather than a formula: the number of paths into a
square is the number into the square above plus the number into the square to
its left, because those are the only two ways in.

```ruby
# Фигурата е съставена от квадратчета, подравнени отляво: в първия — 2, във
# втория — 3, в третия — 3. Кенгурчето е в квадратчето А (горе вляво), а майка
# му — в квадратчето Б (долу вдясно). Кенгурчето се движи от квадратче в
# квадратче само надясно и надолу. По колко различни пътя може да стигне до
# майка си?                                                      → 5
```

**Three answer formats, one type** — 106 problems, all with a figure. The typed
count is the primary shape; the other two exist because the *method* is worth
making the student perform:

| family | format | rungs | what it asks |
|---|---|---|---|
| `paths.staircase` | typed + `figure:` | 1150–1930 (7) | the number of paths from А to Б |
| `paths.staircase_table` | `grid_fill` + `figure:` | 1050–1570 (5) | the count table itself — 1s pre-filled down the first row and column, squares outside the figure (and the crossed-out one) pre-filled `0`, the rest blank |
| `paths.staircase_moves` | `blanks` + `figure:` | 1200–1850 (6) | the count *and* how many moves a path takes — `(rows − 1) + (last width − 1)`, the same for every path, which is exactly what the student who answers "6 пътя, защото 6 хода" has confused |

Topic `Броене и комбинаторика`, area `interactive_kangaroo`, all three in
`families/interactive_kangaroo.rb` behind one `Staircase` module. The `grid_fill`
variant stops at 1570 and at a 4×4 grid: at most 5×5 and 8 blanks, or the widget
stops being a maths exercise (§3.3).

**The ladder** — the count is not the difficulty. The number of rows is, and so
is a crossed-out square; a count above ~30 matters only because it is what stops
a student listing the paths one by one instead of filling the table. What each
rung of `paths.staircase` draws:

| Elo | rows | widths up to | crossed out | count in |
|---|---|---|---|---|
| 1150 | 2 | 6 | — | 3–6 (one path drawn in, as the sheet does) |
| 1280 | 3 | 4 | — | 4–15 |
| 1410 | 3 | 5 | — | 6–30 |
| 1540 | 4 | 5 | — | 8–45 |
| 1670 | 4 | 6 | — | 12–80 |
| 1800 | 4 | 6 | one square | 8–60 |
| 1930 | 5 | 6 | one square | 15–130 |

Each rung also carries a `min_last` — the last row has to be at least so wide.
That is not difficulty, it is what keeps a rung's shapes out of the space of the
rung below: the importer keys questions by their text, so two rungs drawing from
the same pool of figures leave the upper one empty rather than merely repetitive.

**What the builder has to guarantee.** Like the deduction families in §5b, this
one needs a solver rather than a formula — a staircase with a hole has no
binomial — and the solver is checked against brute force:

1. Widths **non-decreasing** downwards, first ≥ 2, last ≤ 6, 2–5 rows. That is
   what makes Б exist and makes it reachable; a figure that narrows has no
   bottom-right square to walk to.
2. The table's answer is compared with a **full enumeration** of the paths
   (≤ 30 squares, so walking every path costs nothing) and the variant is
   dropped on a mismatch. Two counts of one thing, one of them dumb.
3. Count between 3 and ~120: two paths is not a question, and nobody verifies
   a hundred and fifty.
4. Above the bottom rung, at least one strict step in the widths — otherwise it
   is a rectangle and the answer is a binomial coefficient the top of the ladder
   can look up.
5. A crossed-out square sits strictly inside: never А or Б, never in the first
   or last row (there it would only shorten the figure), and never in the left
   column, which is where the method's column of 1s comes from — the explanation
   says "по лявата колона се стига само по един път" and that has to be true.
6. The example path, drawn only on the bottom rungs, is taken *from* the
   enumeration, so it cannot be an illegal path.
7. The stem spells out the row widths and the blocked square in words. The views
   render question images with an empty `alt`, and the importer keys questions by
   their text — one sentence does both jobs.

**Explanation and hints.** The explanation fills the table row by row (a crossed
square prints as `×`) and ends on the number in Б; `watch:` names the two
mistakes the type is built to catch — multiplying instead of adding, and
answering with the number of *moves* (constant) instead of the number of paths.
`check:` re-adds the two squares feeding Б, and has to say when there is no
square above it at all: in a staircase the row above Б is usually narrower, and
"the number above it (0)" would send the student looking for a square that is
not there.
The hint ladder is the method without a number in it: *into a square you come
only from above or from the left, so add those two*; then *write 1 in А and fill
the whole first row and first column*; then *fill row by row — a square outside
the figure, or a crossed-out one, contributes 0*. None of them states the count.

**The figure** — `Figures.staircase_grid(widths:, blocked: [], path: nil)`,
drawn like the printed sheet: thin interior lines, a **bold outline** on every
edge whose neighbour square is missing, А shaded in `FILL` with an indigo
letter, Б in `ACCENT_FILL` with a red one, a blocked square grey with a cross,
and the optional example path in `ACCENT`, trimmed by about a third of a square
at both ends so it neither covers the letters nor lands on the mother — the
arrow stops at the edge of her square, as the original does. A crossed-out
square keeps a white ground: `rasterize.sh` quantizes to 32 colours and returns
a light grey as dither noise, so the cross carries the meaning on its own.

## 5d. Counting the squares taken out of a square (Кенгуру №4)

The type: a square cut into n × n little squares with a piece of it taken away.
How many little squares are gone? What makes it a problem rather than a count is
that **the missing squares are not drawn** — only a dashed contour says how big
the square was — so there are two ways through it, counting the holes against a
grid the student has to impose themselves, or counting what is left and taking it
from n². The second is the method worth learning, and it is the one the youngest
child does not think of.

```ruby
# Квадрат е направен от 16 еднакви малки квадратчета — 4 реда по 4. Част от тях
# са махнати; оцветените на чертежа са останалите. Колко квадратчета са
# махнати?                                                            → 6
```

**Two answer formats, one type** — 96 problems, all with a figure, topic
`Броене и комбинаторика`, area `interactive_kangaroo`, both behind one
`PunchedSquare` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `count.punched_square` | typed + `figure:` | 700–1310 (6) | how many little squares are gone |
| `count.punched_square_parts` | `blanks` + `figure:` | 660–1260 (6) | how many are left **and** how many are gone |

Typed, not multiple choice: the printed sheet offers five consecutive numbers,
which is a 1-in-5 guess, and `ExactValue` parses a count without help. The two
boxes of the second family are the method made visible, the way
`paths.staircase_moves` asks for the paths and the moves (§5c) — and they hand
the student the check the single number cannot, because the two of them have to
add up to the whole square. That is also why the same grid sits a rung *lower*
there: being asked for both counts says that subtracting is what you do.

**The ladder** — the difficulty is the size of the square and how much of it is
gone, plus the scaffolding, which is taken away after the second rung. Both
families draw the same geometry at their own ratings:

| rung | square | махнати | figure |
|---|---|---|---|
| 1 (700 / 660) | 3×3 | 2–4 | faint grid over the empty part |
| 2 (820 / 780) | 4×4 | 4–6 | faint grid over the empty part |
| 3 (940 / 900) | 4×4 | 6–9 | dashed contour only |
| 4 (1060 / 1020) | 5×5 | 9–12 | dashed contour only |
| 5 (1180 / 1140) | 5×5 | 12–15 | dashed contour only |
| 6 (1310 / 1260) | 6×6 | 15–21 | dashed contour only |

This is the cheapest rung the corpus has below 800 that still needs a figure,
which is why the bottom of the ladder is worth keeping: a 3×3 with three holes
and a grid drawn in is a real problem for a six-year-old and a free point for
everyone else.

**What the builder rejects** (each one `raise Authoring::Duplicate`, and the
builder just draws again):

1. Holes in fewer than two rows, or fewer than two columns. A stripe of holes is
   countable without imposing the grid at all, which is the one skill the type
   is for.
2. Holes filling a rectangle — then the answer is a multiplication, a different
   problem that happens to look like this one.
3. No hole touching an edge. Then the remaining shape's own bounding box is the
   whole square, the size can be read off it, and the dashed contour is
   decoration. An edge hole is what makes it load-bearing — and a whole edge row
   of holes, which the upper rungs produce often, is the best version of this
   type.

**The stem** carries n² and n × n in words (16 еднакви малки квадратчета, 4 реда
по 4), because the views render question images with an empty `alt`. It varies
over four framings × six materials — квадратчета, плочки, листчета, картончета,
марки, лепенки, all feminine or neuter so the plural after a number needs no
special counting form. That variation is not decoration: the importer keys
questions by their text, and one fixed stem would collapse the family into a
single question. The framings deliberately read almost the same, so what the
student recognises is the type.

**Explanation and hints.** Both families walk the same three steps — n², the
shaded squares counted row by row, the subtraction — and then part company on
the check, which is the useful difference between the two formats: the typed one
counts the *holes* row by row instead (two counts of one thing, the second
independent of the first), the two-box one adds the boxes back up to n². Their
`watch:` lines follow the same split: the typed family names the answer the type
is built to catch, the number of *shaded* squares, and then the row that is
entirely gone — it is still a row of the square, and the dashed line is the only
thing saying so; the two-box family says what a sum that misses n² means, a
square counted twice or skipped. The hint ladder is shared, the method with no
number of its own in it: *the missing ones are not drawn, the dashed contour
shows how far the square reached*; then *count the shaded ones row by row so none
is missed or counted twice — the whole square has n² of them*; then *the missing
ones are what is short of n²*.

**The figure** — `Figures.punched_square(size:, kept:, guides: false)`. Kept
cells are `SHADE` with an `INK` outline drawn cell by cell, so neighbours share a
solid line the way the printed sheet has them; the whole square is a dashed
`MUTED` rectangle; the missing cells are simply not drawn. `guides:` adds the
faint dashed grid over the empty part — the two lowest rungs keep it, and because
the kept cells are drawn over it, it shows up exactly where the counting happens.

## 5e. Which body cannot be glued from the two pieces (Кенгуру №10)

The type: two little constructions of glued unit cubes are drawn — one of 3
cubes, one of 2 — and five bodies below them. Which body cannot be built by
putting the two together? It is the one purely **spatial** type in the corpus:
every body has the same number of cubes, so counting decides nothing, and the
work is to find the *cut* — where the smaller piece sits inside the body so that
what is left is exactly the bigger piece.

```
# Горе на чертежа са двете фигури — от 3 и от 2 пластмасови кубчета. Под черта
# всяко тяло е от 5 кубчета. Кое от телата А, Б, В, Г и Д НЕ може да се получи,
# като двете фигури се долепят една до друга?                            → А
```

**Two answer formats, one type** — 96 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both behind one `CubeChoice`
module over the `Cubes` solver:

| family | format | rungs | what it asks |
|---|---|---|---|
| `solids.glue_impossible` | `options:` А–Д + `figure:` | 1150–1700 (6) | which body cannot be built — the sheet's own question |
| `solids.glue_buildable_pick` | `multi_select` + `figure:` | 1200–1760 (6) | every body that **can** be built |

The choices are letters, which no other family does, and the reason is
mechanical: a question carries **one** image, so the five bodies live in one
plate and the letters under them are what the student can point at. The second
family exists because with a single letter to find, whoever spots it stops
thinking about the other four; there the number of impossible bodies is 1, 2 or 3,
varied on purpose so the count is not a tell.

Topic: `Логически задачи` is the closest the tree comes. `Обем` is about volume
formulas and nothing here is a calculation — the cube counts are equal by
construction.

**The ladder** — the pieces get bigger and the bodies leave the plane:

| rung | pieces | body | bodies drawn |
|---|---|---|---|
| 1 (1150 / 1200) | 3 + 2 | 5 cubes | flat only |
| 2 (1250 / 1310) | 3 + 2 | 5 cubes | flat or two levels |
| 3 (1360 / 1420) | 4 + 2 | 6 cubes | flat only |
| 4 (1470 / 1530) | 4 + 2 | 6 cubes | flat or two levels |
| 5 (1590 / 1650) | 4 + 3 | 7 cubes | flat only |
| 6 (1700 / 1760) | 4 + 3 | 7 cubes | flat or two levels |

The pieces are the domino, the L-tromino („ъгъл") and the L-tetromino
(„Г-образна фигура") — all **flat** pieces, and that is a decision, not a
shortage of ideas. A flat piece is mirrored by a 3D rotation, so the set of
buildable bodies stays closed under mirroring and no body is impossible merely
for being the wrong way round: that would be a puzzle about handedness, not
about assembly.

**The solver, and why it is trustworthy.** `Cubes.buildable(small, big)` glues:
it fixes the big piece, takes the small one in each of its distinct orientations
(of the 24 rotations of the cube — reflections are absent, a physical piece
turns but does not mirror) and places it so one of its cubes lands on a face
neighbour of the big piece, which is exactly what "glued along a whole face"
means and covers every assembly there is. `Cubes.cuts(body, small, big)` goes
the other way: it lifts the small piece out of a finished body wherever it fits
(anchoring the piece's first cube on each cube of the body finds every
placement) and classifies what is left — the body falls apart, the wrong shape
remains, or the big piece does. The two directions must agree on every body
either of them names, and they do: 875 bodies across the three piece pairs, no
disagreement. That is what makes an answer key of "cannot be built" honest.
The bodies that cannot be built are grown at random from a fixed seed and sieved
through `buildable` — the pool is the same on every rebuild, and enumerating all
1023 heptacubes to find them is not needed.

**What the builder rejects**, all of it in service of one thing — the answer
must not be findable without assembling anything:

1. **A mixed plate.** All five bodies are flat, or all five have two levels. On a
   mixed plate the odd one out can be picked by eye.
2. **An impossible body of its own size.** Every impossible body is paired with
   a buildable one of the same bounding box, so the answer is not simply the
   body shaped differently from the rest. Two impossible bodies of the same
   bounding box share one twin, which is how three of them fit beside two
   buildable ones.
3. **A mirror pair among the five.** Two bodies that are mirror images are
   genuinely different bodies but the same drawing seen the other way round, and
   the reader would be guessing.
4. **A body with a hidden cube** (see the figure note below).

**Explanation and hints.** The explanation is the solver's case analysis in
words: how many places the small piece sits in the body, how many of them break
it into two parts, how many leave the wrong shape, how many leave the piece. The
impossible body gets that tally with a zero at the end, the other four get their
number of good cuts, and `check:` walks one buildable body through the same
count so the method is shown working where the answer is known. `watch:` names
the two traps: the cube counts are all equal, so nothing is decided by counting,
and cubes in another arrangement are not the same piece — it may be turned, not
bent. The hint ladder is the method with no body named in it: *all the bodies
have the same number of cubes*; then *the cut is big + small, find the small
piece inside the body and take it out*; then *what is left must be exactly the
big piece, so try every place the small one fits*.

**The figure** — `Figures.cube_choices(pieces:, candidates:, labels:)`, with
`draw_cubes` doing the projection: cell (x, y, z) is a unit cube, +x runs
down-right on the page, +y down-left, +z up, so every cube shows three faces
(top, +y on the lower left, +x on the lower right) and painting the cubes in
order of x + y + z gets the occlusion right, because that sum is the distance
from the eye. The plate is the two pieces, a rule, then the bodies in rows of
three with their letters under them, a short last row centred.

The drawing is not allowed to lie. A cube whose +x, +y and +z neighbours are all
present has all three of its visible faces covered and **disappears from the
picture** — a body drawn that way would be counted wrong by the reader, so
`Cubes.display` picks, among the 24 orientations, one with no hidden cube (and
among those, the flattest with the most cubes on the ground, so the bodies stand
rather than float). A body with no honest orientation at all is dropped. Checked
over every body the two families draw: 878 of them, none hidden, none drawn
taller than it needed to be.

## 5f. How many triangles are in the figure (Кенгуру №15)

**Status: written, not generated.** The family and its solver are in
`families/interactive_kangaroo.rb` and the figure builder in `lib/figures.rb`,
but the corpus has *not* been rebuilt with them: `db/seeds/ladders` and the
question bank hold nothing from this family yet. Everything below is the spec it
generates against, verified by running the family — 48 problems, six full rungs —
without writing them out. To ship it: `ruby tools/authoring/build.rb`, then
`rasterize.sh`, `check.rb`, and the import.

The type: a square (or a rectangle, or a triangle) with two to four more
segments drawn across it — how many triangles are in the figure? Nothing is
measured and nothing is calculated. The whole difficulty is *systematic*
counting, and the type is built on one mistake: a triangle with a line running
through it is still a triangle, and it is the one that gets missed.

```
# В правоъгълника ABCD са начертани диагоналът AC и отсечката DE, където E е
# средата на AB. Колко триъгълника има на чертежа?                        → 6
```

One family, `count.triangles_in_figure`, 48 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`. Typed, not the five consecutive
options the printed sheet offers — those make it a one-in-five guess, and
`ExactValue` parses a count without help.

**Every crossing is lettered**, which the printed sheet does not do, and it
changes the problem for the better. The stem can then say exactly what is drawn
(„диагоналът AC и отсечката DE, където E е средата на AB") instead of pointing
at a picture, the worked solution can list the triangles by name instead of
waving at them, and the letters are what gives the family its text variety — the
construction differs every time, so no two stems collide. Corners keep A, B, C,
D; points on the sides get E, F, G, H; crossings inside get M, N, P, Q, top to
bottom then left to right.

**The ladder** — more segments, then a base that is not a square:

| Elo | cuts | base | answers |
|---|---|---|---|
| 950 | 2 | square | 3–4 |
| 1080 | 2 | square, rectangle, triangle | 6–8 |
| 1200 | 3 | square, rectangle | 7–9 |
| 1320 | 3 | + triangle | 10–12 |
| 1450 | 3 | + triangle | 13–14 |
| 1580 | 4 | square, rectangle | 17–21 |

A cut runs corner to corner (a diagonal, and only between corners that are not
neighbours — otherwise it is a side), corner to a point on a side it does not
touch, or point on a side to point on another side. The triangle base is dropped
from the top rung: with four segments across it the crossings crowd together and
the figure stops being readable well before it stops being countable.

**Exact rational arithmetic, not floats.** Whether three lines meet at one point
is the difference between 12 triangles and 16, and in floating point that gets
decided by rounding. Every coordinate here is a `Rational`.

**A vague point has to be an honest one.** When the stem describes a point only
as „точка от страната BC", the count is recomputed with that point moved to four
other places along its side; if the answer changes anywhere, the figure is
thrown away. A point pinned as „средата на BC" skips the check, because the stem
already says where it is. That is what makes a stem which does not give
coordinates a complete question.

**What else the builder rejects:** two crossings closer than 0.11 of the base
(a drawing nobody can read), a segment lying along a side of the shape (it draws
nothing new), a repeated segment, a figure whose triangle count is outside the
rung's band, and one needing more interior letters than there are. Most draws
die on one of these, so the family redraws up to 24 times from the rung's own
RNG before giving up on a variant — a rebuild redraws the same figures.

**How the counting works, twice.** `Arrangement#triangles` takes every triple of
drawn segments and keeps the ones whose three pairwise crossings are three
different points; each side of that triangle then runs between two points of one
drawn segment, so it is drawn, and nothing has to trace regions. The check on
that is a second counter with nothing in common but the answer: every triple of
*lettered points*, kept when each of the three connecting pieces lies inside some
drawn segment and the three are not collinear. The two agree on all 284 figures
they were run over, and every claim a stem makes about a point was
re-verified geometrically — none false.

**Explanation and hints.** The explanation lists the triangles grouped by size,
smallest first, and totals them as a sum of those groups
(„1 + 1 + 1 + 1 + 2 = 6") — which is the systematic method's own arithmetic.
`check:` splits the total into whole triangles and ones with a line through them,
and `watch:` names the biggest divided triangle in *this* figure, computed rather
than asserted: a triangle counts as divided when some drawn segment crosses its
boundary twice with the midpoint of those crossings strictly inside, so a segment
merely running along a side does not count. The hint ladder is the method with no
figure-specific number in it: *the count is not visible at once, so count
systematically*; then *the smallest triangles first, the ones with no line
through them*; then *the bigger ones — a triangle split by a line is still a
triangle*.

**The figure** — `Figures.segment_art(nodes:, segments:)`. Coordinates arrive as
unit fractions with y pointing up, the way the geometry is written, and are
scaled and flipped once. Corner and side letters sit outside the shape, pushed
away from its centre; a letter for a crossing *inside* the figure would land on
the lines, so it gets a white disc under it and a dot to say which crossing it
names.

## 5g. Minutes when exactly two are on (Кенгуру №5)

**Status: written, not generated.** The two families and the `Schedule` module
are in `families/interactive_kangaroo.rb`, the chart builder is
`Figures.timeline_bars`, and nothing from either is in `db/seeds/ladders` or the
question bank. Verified by running them — 96 problems, twelve full rungs — and
checked by hand against the source problem. To ship: `build.rb`, `rasterize.sh`,
`check.rb`, import.

The type: a lighting plan drawn as bars against a minute axis — three lights,
each switching on and off a few times — and the question is how many minutes
**exactly two** of them are lit. The whole problem turns on that word. The
minutes when all three are lit are not among them, and they are exactly the ones
a quick reader adds in.

```
# Осветител в театъра запалва и гаси светлините по показаната схема: светлина А
# свети от 1 до 5 и от 6 до 9; светлина Б — от 2 до 6 и от 7 до 12; светлина В —
# от 0 до 3, от 5 до 8 и от 10 до 12 (в минути). Колко минути общо точно две от
# светлините светят едновременно?                                          → 8
```

**Two answer formats, one type** — 96 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both over one `Schedule` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `count.overlap_minutes` | typed + `figure:` | 900–1500 (6) | the minutes with exactly two on (and, low down, both / none / at least one) |
| `count.overlap_split` | `blanks` + `figure:` | 960–1560 (6) | a box per count: exactly one, exactly two, all three |

**Every switch is on a whole minute**, so a minute is entirely one state or
entirely another and the answer is a count rather than a measurement. That is
what makes the method — walk the plan minute by minute, write down how many are
on, then add up the minutes of the kind asked for — exact, and it is what the
explanation does.

**The schedule is written out in the stem as well as drawn.** Two reasons, and
the second matters more. The corpus rule is that every number in a figure
appears in the text, because the views render question images with an empty
`alt`. And the type's real work is the interval logic, not reading a chart to
the nearest pixel — spelling the plan out moves the difficulty to where the
problem actually is. It also solves the family's text problem for free: the
schedule differs every time, so no two stems collide.

**The ladder** — the question changes as well as the size, which is unusual for
this catalogue and deliberate here: „both" and „none" are the same reading with
an easier question on top of it.

| Elo | lanes | span | runs per lane | question |
|---|---|---|---|---|
| 900 | 2 | 8–10 | ≤2 | both, or neither |
| 1020 | 3 | 10–12 | ≤3 | all three, none, at least one |
| 1140 | 3 | 12 | ≤3 | exactly two |
| 1260 | 3 | 13–16 | ≤4 | exactly two, all three |
| 1380 | 4 | 16 | ≤4 | exactly two, exactly three |
| 1500 | 4 | 17–20 | ≤4 | exactly three, exactly two |

`count.overlap_split` runs the same geometry one rung higher throughout and
stops at three lanes: four boxes is a form, not a question.

**What the builder rejects.** Run lengths scale with the span, so a
twenty-minute plan does not end in five minutes of empty chart, and on top of
that:

1. **An answer of nought, or of nearly the whole span** — the answer has to sit
   between the rung's floor (2 low down, 4 at the top, which is what pushes the
   upper rungs toward busier plans) and span − 2.
2. **A lane on almost always, or almost never** — every lane is lit between 30%
   and 80% of the plan, or it is not worth a lane.
3. **Nothing on in the last two minutes.** The chart has to use the axis it
   draws; an empty tail reads as a broken picture, not as a plan that ends early.
4. **„Exactly two" where no minute has three on.** Then it means „at least two",
   and the word the whole problem turns on does no work. Same guard for exactly
   three.
5. **Two identical lanes**, and for the breakdown family, a row of boxes where
   only one has a number in it.

**Explanation and hints.** Step one is the whole analysis in one line — the
count of lit lanes for each minute of the plan, `2 3 2 1 3 2 0 1 3 1 1 1` — which
is compact, complete and checkable against the chart. Step two merges the
minutes of the asked-for kind back into intervals and adds their lengths
(„точно две работят в 0–1, 2–3 и 5–6 — 1 + 1 + 1 = 3 минути"). `check:` is the
part that makes the type self-verifying: the minutes with none, one, two and
three on must add up to the span, and the explanation prints that sum. `watch:`
names the trap in the problem's own numbers — „точно две" is not „поне две", and
here that is *n* minutes' difference. The hint ladder is the method with no
number from the figure in it: *nothing changes inside a single minute*; then
*write above each minute how many are on*; then *add only the minutes with
exactly as many as the question asks — a minute with more does not count*.

**The figure** — `Figures.timeline_bars(lanes:, span:, unit:)`. One lane per
switchable thing, a letter at its left, bars in the corpus indigo ramp rather
than a colour per lane: the lanes are told apart by position and by their
letter, which is what a sheet printed in one colour has to do anyway. Vertical
rules at every minute, the axis numbered every minute or every second minute
depending on how wide a minute lands, and the unit under it. Minute scale is
clamped to 17–34 px so a 20-minute plan is the same width on the page as a
12-minute one.

## 5h. Which weight is standing beside the balance (Кенгуру №10, another sheet)

**Status: written, not generated.** The two families and the `Balance` module are
in `families/interactive_kangaroo.rb`, the drawing is
`Figures.balance_scale`/`draw_weight`, and neither family has been built into
`db/seeds/ladders` or the bank. Verified by running them — 80 problems, ten full
rungs — and every puzzle brute-forced (below). To ship: `build.rb`,
`rasterize.sh`, `check.rb`, import.

The type: weights of 1, 2, … n kilograms, all different, most of them on a
balance that is level and one standing beside it — which weight is the one
standing beside it? Nothing is weighed and nothing is estimated from the
drawing. A level balance is exactly one equation, the two pans hold equal sums,
and that plus the parity of the total is the whole method.

```
# Рени има тежести от 1, 2, 3, 4, 5 и 6 килограма — всяка различна. Рени
# балансира везната с 5 от тях и оставя една встрани. На лявото блюдо са
# тежестта от 5 кг и още две без надпис, а на дясното — тежестта от 6 кг и още
# една без надпис. Колко килограма е тежестта извън везната?               → 1
```

Worked: the six weights total 21, so with x standing aside the scale holds
21 − x split into two equal pans and 21 − x must be even — x is odd, so 1, 3 or
5. The 5 is on the scale. And x = 3 would need each pan at 9, so the left pan
would need 4 more from {1, 2, 4} with two weights: 1 + 2, 1 + 4 and 2 + 4 give
3, 5 and 6, never 4. So x = 1, and indeed 5 + 2 + 3 = 10 = 6 + 4.

**Not to be confused with `logic.balance`** in the `logic` area (§10.19) — 36
typed problems about a balance with *unnumbered* weights ("една голяма тежест
уравновесява 2 малки, колко малки за 2 големи"), which is a proportion dressed as
a scale. This type has numbered, all-different weights and is a deduction. Two
families about balances is right; two families about the *same* balance would not
be, which is what §10 is there to catch.

**Two answer formats, one type** — 80 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both over one `Balance` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.balance_aside` | typed + `figure:` | 1000–1600 (6) | the weight standing beside the scale |
| `logic.balance_fill` | `blanks` + `figure:` | 1060–1510 (4) | every weight with no number on it, each carrying a letter |

**Only some weights show their number.** That is what makes it a puzzle rather
than a reading exercise, and it is also the thing the builder has to be careful
about: the answer must be *forced* by what the picture shows. `possible_asides`
enumerates every weight that could be the one aside, given the numbers printed,
how many blanks sit on each pan and that the pans are level, and the puzzle is
kept only when that comes back as a single value.

**Testing one pan is enough**, which is worth writing down because it is what
keeps the solver simple: if the left pan can be made to reach half of what is on
the scale with the number of blanks it has, the right pan holds the rest and
reaches the same half automatically. So the whole condition is a subset-sum over
the left pan's blanks — and the same fact is what makes the explanation's case
analysis honest and short.

**The check.** A second, dumber method brute-forces *every* placement — which pan
each unlabelled weight sits on, which one is left out — and confirms the asked
weight is identical across all of them. Over 313 puzzles from both families: no
disagreement, and for the lettered version the whole arrangement came out forced,
not just the weight aside.

**The ladder.** `logic.balance_aside` grows on two knobs, the number of weights
and how many of the ones on the scale hide their number:

| Elo | weights | blanks on the scale |
|---|---|---|
| 1000 | 5 | 2 |
| 1120 | 6 | 2 |
| 1240 | 6 | 3 |
| 1360 | 7 | 3 |
| 1480 | 7 | 4 |
| 1600 | 8 | 4 |

`logic.balance_fill` has **four** rungs, not six, and the reason is a property of
the format rather than a shortage of ideas: two blanks on one pan are
interchangeable, so a letter on either of them cannot be pinned down, and a
letter nobody can determine is not a question. With at most one blank per pan the
only knob left is the number of weights (5, 6, 7, 8) — and once the weight aside
is known, each pan's blank follows by subtraction, which is a different and
cleaner piece of reasoning than the search the typed family asks for.

**What else the builder rejects:** a pan with no number on it at all (a picture
that says nothing), a puzzle where parity alone settles the answer (fewer than
two candidates survive the even/odd test, so there is nothing to work out), and
pans outside two to four weights, which is what the drawing can hold.

**Explanation and hints.** The explanation is the argument above, generated: the
total, the parity line, the surviving candidates, then one sentence per losing
candidate naming the sums its left pan could reach and the one it needed, and
finally the arrangement that works with both pans added up. `check:` is
half + half + aside = total. `watch:` names the trap that costs the most time —
not every weight *can* be the one aside, so parity comes first and the trials
second. For the lettered family `watch:` names the other misreading: the pans are
equal in **sum**, not in number of weights. The hint ladder is the method with no
candidate in it: *a level balance means equal sums, however many weights are on
it*; then *the total is n, and one weight leaves the scale — what does that mean
for what is left*; then *try the values one at a time, checking whether the left
pan can reach exactly half*.

**The figure** — `Figures.balance_scale(left:, right:, aside:)`, with
`draw_weight` for the little jar shape the sheets draw, labelled with a number, a
`?`, a letter, or nothing. The pans hang the same distance from the fulcrum
because that is what a level balance means, so the beam is drawn symmetric about
the wedge even when one pan holds more weights than the other. The weights are
white with an ink outline rather than filled: `rasterize.sh` quantises to 32
colours and a very light fill comes back as dither noise. The weight left out
stands beside the scale on nothing, as it does on the sheet — it is not part of
the balance and should not look like it is.

## 5i. Houses on the sides of two roads (Кенгуру №11)

**Status: written, not generated.** The two families and the `Roads` module are in
`families/interactive_kangaroo.rb`, the drawing is
`Figures.island_roads`/`draw_compass`, and neither family is in
`db/seeds/ladders` or the bank. Verified by running them — 80 problems, ten full
rungs — and the determinacy test checked against brute force (below). To ship:
`build.rb`, `rasterize.sh`, `check.rb`, import.

The type: two roads cross an island and the houses are counted by *side* — so
many north of road A, so many east of road B — with one of the four counts
missing. No house is drawn and nothing is measured: the two roads make a two by
two table whose margins are given, and the question asks for a margin the table
forces.

```
# Седем къщи се намират на север от път A, осем къщи са на изток от път B, а пет
# къщи са на юг от път A. Колко къщи се намират на запад от път B?        → 4
```

Worked: north and south of A together are all of them, 7 + 5 = 12; every house is
either east or west of B, and 8 are east, so 4 are west.

**What this type is really about**, and the reason it needs a real check: **the
four quarters are not determined by the sides.** 7 north and 5 south with 8 east
is satisfied by many different quarter counts. The *margin* is forced, a quarter
is not — so the builder decides which questions are askable rather than assuming
the shape of the question makes them so.

**Two answer formats, one type** — 80 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both over one `Roads` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.roads_sides` | typed + `figure:` | 1000–1600 (6) | the missing side, or a quarter where one is forced |
| `logic.roads_quarters` | `blanks` + `figure:` | 1150–1570 (4) | all four quarters, which one extra number makes possible |

**How "forced" is decided.** Every fact says which regions it adds up — "north of
A" adds the two regions of the top band — so a fact is a row of zeros and ones
over the regions. The asked count is forced exactly when its own row is a linear
combination of the given rows, which is what a student does by hand when they add
and subtract the given numbers. `Roads.forced?` answers that with Gaussian
elimination over `Rational`, and every family raises rather than ship a question
whose answer is not in that span.

Checked the dumb way as well: walk every non-negative arrangement of the regions
that agrees with the given numbers and see whether the asked count is the same in
all of them. 240 fact sets, no disagreement with the algebra — including the
negative control, where the sides alone are given and a *quarter* is asked, which
both methods refuse.

**The ladder** — the shape of the question changes, not just the numbers:

| Elo | shape |
|---|---|
| 1000 | two roads, both bands and one side given, the other side asked (the sheet), totals 8–14 |
| 1100 | the same with bigger numbers |
| 1210 | two roads, a *quarter* asked: south band, east side and the north-east quarter are given, so the south-west quarter follows by two subtractions |
| 1320 | three roads — two parallel and one crossing — so the total is a sum of three bands |
| 1430 | the same with bigger numbers |
| 1540 | three roads and **one number more than the question needs**: a quarter count that plays no part, so the work is deciding what to ignore |

That last rung is deliberate. Competition papers do give numbers that are not
needed, and the explanation says so outright — „числото за частта … не участва“ —
because a student who used it and got the right answer anyway has not learnt the
thing.

**What the builder rejects:** any region count of nought (a stem that says "no
houses north of A" reads as a mistake), and any question whose answer is not
forced.

**Explanation and hints.** For a side question the explanation counts the houses
twice, once down the bands and once across the sides, and takes the difference;
`check:` prints both counts as one equality. For a quarter question it is a chain
of two subtractions, and `check:` puts both given numbers back together.
`watch:` is where the type's lesson goes: on a side question, that the individual
quarters are unknown *and unnecessary*; on a quarter question, that a quarter is
counted in both directions, so the numbers subtract rather than add. The
`blanks` family's `watch:` says the thing plainly — without the one quarter
count the puzzle has no single answer. The hint ladder is the method with no
number in it: *the roads cut the island into parts and each house is in exactly
one*; then *each given number is a sum of several parts — find which*; then *all
the houses can be counted two ways, north–south and east–west, and the two sums
are equal*.

**The figure** — `Figures.island_roads(roads:, quarters:, seed:)`. A blob for the
island, smoothed through the midpoints of its own outline (it carries no
information, so it only has to look like an island, and the seed keeps two
problems from sharing a coastline); thick straight roads with a label along each
one, the north-south label rotated and placed in the widest gap between the
east-west roads so it never lands on one; and `draw_compass` beside it, because
"north of road A" means nothing on a page without it. When the question is about
a quarter, the four quarters are lettered СЗ/СИ/ЮЗ/ЮИ in the picture so the words
and the drawing agree.

## 5j. In what order are the stickers met in the maze (Кенгуру №16)

**Status: written, not generated.** The two families and the `Maze` module are in
`families/interactive_kangaroo.rb`, the drawing is `Figures.maze_floors`, and
neither family is in `db/seeds/ladders` or the bank. Verified by running them —
80 problems, ten full rungs — and the claim the answer rests on checked by
simulation (below). To ship: `build.rb`, `rasterize.sh`, `check.rb`, import.

The type: a maze of rooms on one or two floors, doors between some of them,
staircases between the floors, a way in and a way out, and a sticker on the wall
of a few rooms. In what order does the walker meet them?

**The maze is carved as a spanning tree**, so between any two rooms there is
exactly one route with no going back on itself. That is what turns the answer
from a choice into a fact: every sticker sits on that one route, the dead ends
hold nothing, and so the order is the same however much the walker wanders.
Randomised depth-first carving gives the tree; the route is a breadth-first walk
along it.

**Two answer formats, one type** — 80 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both over one `Maze` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.maze_order` | `ordering` + `figure:` | 950–1550 (6) | the stickers in the order they are met |
| `logic.maze_walk` | `blanks` + `figure:` | 1100–1520 (4) | how many rooms the route passes and how many times it changes floor |

`ordering` is the right widget and not a convenience: the answer *is* a sequence,
the printed sheet offers five permutations as pictures, and the view shuffles the
items server-side (`_ordering.html.erb`) so the order never sits in the page.

**Two deviations from the sheet, both deliberate.**

*The figure is a plan, not the isometric cutaway.* The sheet draws a two-storey
building in 3D with walls, black doors and staircases. That drawing is a picture
of a building; a plan is a picture of the problem, it is unambiguous about which
rooms connect, and it survives being 350 pixels wide on a phone, which the
cutaway would not. A wall is a line, a door is the gap in it, stairs are the
hatched square, a sticker is its own word inside the room. The way in points at
its wall and the way out points away from it — an arrow into a wall labelled
„изход" reads as another entrance, and the sheet draws them that way too. A
single-storey maze gets no caption under its plan: „партер" only means something
when there is a floor above it. The margins are as deep as the openings need,
since a north-facing way puts its arrow and its word above the plan and a
south-facing one puts them below, where the caption also goes.

*The figure is load-bearing.* This is the one type in the catalogue where the
stem cannot carry the figure's content: a maze does not go into a sentence, and
listing the doors as coordinates would replace the tracing with bookkeeping —
which is the skill the problem is about. So the corpus rule that every number in
a figure appears in the text is not met here, and it is worth knowing rather
than glossing: a reader who cannot see the plan cannot do this type. What the
stem *can* carry it does — the rules of the maze, the rooms per floor, how many
staircases there are — and that last number is also what keeps two mazes from
sharing a stem, since the layout itself cannot.

**The ladder** — one floor before two, then more rooms, then more stickers:

| Elo | floors | rooms per floor | stickers |
|---|---|---|---|
| 950 | 1 | 3×3 | 3 |
| 1070 | 1 | 3×4 | 3 |
| 1190 | 2 | 2×3 | 3 |
| 1310 | 2 | 3×3 | 3 |
| 1430 | 2 | 3×3 | 4 |
| 1550 | 2 | 3×4 | 4 |

`logic.maze_walk` is two floors throughout, because on one floor its second
number is always nought, and its rungs raise the length of the route (at least 5,
6, 8, 10 rooms) rather than the number of stickers — it draws none.

**What the builder rejects:** a route that never uses the stairs (the upper floor
would be decoration), a maze with no sticker upstairs (same reason), a sticker in
the first or last room, and a route shorter than the stickers need. The way in
and the way out go on **opposite** sides of the building, as the sheet places
them: it reads better and it keeps the route from being three rooms long.

**The check.** Three things worth not trusting, all tested: that the doors really
form a tree (edges = rooms − 1 and every room reached), that the route the family
reports is walkable through actual doors, and that the stickers all sit on it.
Then the claim the answer rests on, by simulation rather than argument: 2,400
*wandering* walks — random moves, down dead ends and back — that reached the exit,
every one of them meeting the stickers in exactly the order the answer gives.

**And the drawing needs its own check, which is the lesson this type taught.**
All of the above passed while the figure was wrong: `maze_floors` took a flag
meaning "this wall has a gap in it" and was handed `!open`, so every wall *with*
a door came out solid and every wall *without* one came out with a gap. The plan
was the exact complement of the maze — a picture in which the answer's route
cannot be walked — and no test of the maze could see it, because the maze was
right. What catches it is a test of the *picture*: parse the wall segments back
out of the SVG, ask for every pair of adjacent rooms whether the wall between
them is drawn with a gap, and compare against the doors the layout says exist;
then walk the answer's route through the drawn gaps and the drawn staircases.
720 interior walls and 40 routes, no disagreement. A figure that carries the
whole question has to be verified like one — the same reason `Cubes.display`
refuses an orientation with a hidden cube (§5e).

**Explanation and hints.** The explanation prints the route as directions —
„надясно, нагоре по плана, по стълбите на горния етаж, …" — which is what a
reader can check against the plan, then names which room along the route each
sticker sits in, then the order. `check:` is the tree property in words: the dead
ends hold no stickers, so wandering cannot change the order. `watch:` names the
misreading the type invites — the order is along the *route*, not down the plan
and not by floor, so a sticker that looks close to the exit can be the first one
met. For the counting family, `check:` splits the moves into doors and stairs and
adds them back up, and `watch:` says why the rooms are one more than the moves.
The hint ladder never mentions a room: *start at the way in and move only where
the wall is broken*; then *at each branch, see where it leads — only one way reaches
the exit*; then *the stairs are a way too* (or, on one floor, *mark the stickers
as you pass them*).

## 5k. Which two pieces assemble the puzzle (Кенгуру №4, another sheet)

**Status: written, not generated.** The two families and the `Tiling` module are
in `families/interactive_kangaroo.rb`, the drawing is
`Figures.puzzle_pieces`/`draw_piece`, and neither family is in
`db/seeds/ladders` or the bank. Verified by running them — 80 problems, ten full
rungs — and the tiling test checked against brute force (below). To ship:
`build.rb`, `rasterize.sh`, `check.rb`, import.

The type: four pieces of a jigsaw are drawn, all with the same number of squares,
and exactly one *pair* of them assembles the square (or rectangle) beside them.
Nothing is calculated — the counts are equal by construction, so counting sorts
nothing out — and the only way through is to try the pairs.

```
# Разполагате с 4 части от пъзел (на чертежа). Всяка част е от по 8 квадратчета
# и се вписва в правоъгълник: част 1 — 3 на 4, част 2 — 4 на 3, част 3 — 3 на 4,
# част 4 — 3 на 4. Частите могат да се въртят и да се обръщат. С кои две от тях
# може да се сглоби квадратът 4 на 4?                                → 1 и 3
```

**Pieces may be turned and turned over.** The stem says so and the solver works
under the same rule — all eight symmetries of the square — so a piece is never
wrong merely for being the mirror of what fits. It is a decision, not an
oversight: a cardboard puzzle piece can be flipped, and leaving it ambiguous
would make some answers arguable.

**Two answer formats, one type** — 80 problems, all with a figure, topic
`Логически задачи`, area `interactive_kangaroo`, both over one `Tiling` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.puzzle_pair` | `multi_select` + `figure:` | 950–1550 (6) | the two pieces that assemble the board |
| `logic.puzzle_hole` | `options:` 1–4 + `figure:` | 900–1290 (4) | which piece fills the hole left by one already placed |

**Testing one piece is enough**, which is what keeps the solver short: lay piece
A in every position it fits, and compare the *leftover* with piece B's canonical
form over the eight symmetries. If the leftover is B, the pair tiles; no search
over B's placements is needed. Cross-checked the slow way — lay both pieces
everywhere and ask whether the two together cover every cell exactly once — over
240 pairs, with no disagreement, and on every plate the pair the question names
is the only pair that tiles.

**The second family exists because the obvious one cannot be posed.** The natural
companion would be „shade the cells piece 1 covers", on the board, with
`grid_shade` — and it has no single answer: a square board has eight symmetries,
so the mirror image of any assembly is another assembly, and the piece's cells
are never determined. (The generator says so out loud: with the uniqueness guard
in place it produced nothing at all.) So the question is turned around instead —
one piece is already lying in the board, the hole is what is left, and exactly
one of the four pieces has that shape. That one is correct **by construction**
rather than by search: a single piece filling a fixed region must be congruent to
it, and the three distractors are checked to be non-congruent.

**The ladder** — a bigger board, then more pieces to pair up:

| Elo | board | cells per piece | pieces shown |
|---|---|---|---|
| 950 | 3×4 | 6 | 4 |
| 1070 | 4×4 | 8 | 4 |
| 1190 | 4×5 | 10 | 4 |
| 1310 | 4×6 | 12 | 4 |
| 1430 | 4×5 | 10 | 5 |
| 1550 | 4×6 | 12 | 5 |

Five pieces means ten pairs to consider rather than six. A 2×4 board was in the
ladder first and had to come out: only four tetrominoes fit in it at all, so
"exactly one pair of four distinct pieces" is not satisfiable — the generator
returned nothing, which is the right way to find that out.

**What the builder rejects:** a piece that is a plain rectangle (the reader sees
that cut without trying anything), two pieces of the same shape among those
shown, a piece that does not fit the board in any orientation (it would be
eliminated by eye, not by thought), and any plate where more than one pair tiles
or none does.

**The stem carries the bounding boxes** — „част 1 — 3 на 4" — for two reasons.
It is what a reader can check against the drawing, and it is what keeps two
plates from sharing a stem, since the shapes themselves cannot go into a
sentence. Like §5j, this type needs its figure; unlike §5j, the stem can at least
carry the piece count and each piece's box, and because every piece is
guaranteed to fit the board, those boxes eliminate nothing on their own.

**Explanation and hints.** The explanation names the pair, says how many
placements assemble the board (including the turned and flipped ones), lists the
pairs that fail and why — at every position a hole is left that the other piece
does not cover — and `check:` adds the two piece sizes back up to the board.
`watch:` names the two traps: the square count does not separate the pairs, and a
piece may need flipping. For the hole family the explanation reads the hole out
row by row, gives its bounding box and how many orientations it has, and `watch:`
says to compare shape rather than count. The hints are the method: *look at the
hole, not at the pieces one by one*; then *count the hole's squares in each row —
the piece must have the same rows*; then *compare shapes, not drawings, because
the piece may be turned or flipped*.

**The figure** — `Figures.puzzle_pieces(target:, pieces:, placed:)`. The board on
the first row with its caption, the numbered pieces on the second, sitting on a
common baseline so their heights can be compared, which is half of what the
reader is doing. `draw_piece` outlines every cell thinly and puts a thick line on
every edge with no neighbour, which is what makes a shape read as one piece
rather than a handful of squares. When a piece is already placed, the board is
drawn **white** with only that piece shaded, so the hole reads as a hole.

## 5l. The perimeter of the rectangle hidden in the dots (Кенгуру №13)

**Status: written, not generated.** The two families and the `Lattice` module are
in `families/interactive_kangaroo.rb`, the drawing is `Figures.lattice_dots`, and
neither family is in `db/seeds/ladders` or the bank. Verified by running them —
80 problems, ten full rungs — and the rectangle finder checked against brute
force (below). To ship: `build.rb`, `rasterize.sh`, `check.rb`, import.

The type: dots are marked on the crossings of squared paper and exactly four of
them are the vertices of a rectangle — what is its perimeter? A square of the
grid is 1 cm, so nothing is measured off the drawing; the sides are counted.

```
# Страната на едно квадратче от мрежата е 1 см. Живко отбелязва 12 точки върху
# мрежата 5 на 5 квадратчета и открива, че четири от тях са върхове на
# правоъгълник. Каква е обиколката на този правоъгълник?               → 8 см
```

**The tilted rectangle is the reason this type needs a solver.** A stem that
promises "four of them are the vertices of a rectangle" is only true if there is
exactly one such four, and an *upright* search cannot promise that: four dots can
make a rectangle at an angle, and then the question has two answers. So
`Lattice.rectangles` finds rectangles in any orientation — two pairs of dots that
share a midpoint and a distance are the diagonals of one — and a plate is kept
only when it finds exactly one. A tilted lattice rectangle has an integer
perimeter only in the 3-4-5 cases, so it is never the answer here; it is a hazard
to be excluded rather than a question to be asked, which is exactly why the
search has to see it.

Checked the slow way too: every four of the marked dots, tested for being a
rectangle by the dot products of its sides, in each of the three ways four points
can be joined into a cycle — so nothing tilted can slip past. 60 plates, the two
methods finding the same rectangles every time, and one rectangle per plate.

**Two answer formats, one type** — 80 problems, topic `Логически задачи`, area
`interactive_kangaroo`, both over one `Lattice` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.lattice_rectangle` | typed + `figure:` | 900–1500 (6) | the perimeter in centimetres |
| `logic.lattice_rectangle_pick` | `coordinate_plot`, **no figure** | 960–1350 (4) | the four vertices, clicked |

The second one is the only family in this catalogue that needs no image at all:
`coordinate_plot` draws the lattice and takes the marked dots as its `fixed`
points, so the widget *is* the picture, and the answer is which four of them get
clicked. Its checker compares the placed points as a set, so the order of the
clicks does not matter.

**How the dots are placed.** The rectangle goes down first, upright and inside
the grid; then dots are scattered one at a time and each is kept only if the
plate still has exactly one rectangle. That is a cheap greedy with rejection, and
it is what makes the stem's promise true by construction rather than by luck.

**The ladder** — a bigger grid and more dots to look through:

| Elo | grid | dots | shortest side |
|---|---|---|---|
| 900 | 4×4 | 6–8 | 1 |
| 1020 | 5×5 | 8–10 | 1 |
| 1140 | 5×5 | 10–12 | 2 |
| 1260 | 6×6 | 11–13 | 2 |
| 1380 | 6×6 | 13–15 | 2 |
| 1500 | 7×7 | 14–17 | 2 |

From the third rung the rectangle is at least two squares wide: a
one-square-wide sliver is spotted without looking for it. The number of dots
varies *within* a rung as well as between them, which is also what keeps two
plates from sharing a stem — the dots themselves cannot go into a sentence, so
the stem carries the grid and the count.

**This is the third type whose figure is load-bearing** (§5j, §5k, and this one),
and the one where it costs least: the `coordinate_plot` family is the same
question with the picture built into the widget, so a reader who cannot see an
image has a way through the type after all.

**Explanation and hints.** The explanation names the four vertices as
coordinates, says which two rows and which two columns they sit in, reads the two
sides off the grid and doubles their sum; `check:` says the other dots make no
rectangle, which is why the four are the four. `watch:` names the two mistakes:
the perimeter is twice the sum and not the sum, and four dots are not a rectangle
merely for being four. The hints are the search: *look for four dots, not at all
of them*; then *two in one row with two directly below them*; then *the perimeter
is twice the sum of the sides, and a square of the grid is 1 cm*.

**The figure** — `Figures.lattice_dots(cols:, rows:, dots:)`: the plain grid and
red dots of the printed sheet, in `ACCENT` with an ink outline so they read on
the lines they sit on. Coordinates count from the bottom left, like the
mathematics, and are flipped once in the drawing.

## 5m. The missing number in the square of sums (Кенгуру №18)

**Status: written, not generated.** The two families and the `SumSquare` module
are in `families/interactive_kangaroo.rb`, the drawing is
`Figures.number_square`, and neither family is in `db/seeds/ladders` or the bank.
Verified by running them — 80 problems, ten full rungs — and every square checked
by reading it back out of its own stem (below). To ship: `build.rb`,
`rasterize.sh`, `check.rb`, import.

The type: a square of numbers with one cell empty and one rule — the sum of the
numbers in any row equals the sum of the numbers in **exactly one** of the
columns. What is the missing number?

```
# В квадрат 3 на 3 са записани числата: първи ред 1, 5, 10; втори ред 7, ?, 3;
# трети ред 8, 4, 2. Сборът на числата в кой да е ред е равен на сбора на
# числата в точно една от колоните. Кое е липсващото число?               → 5
```

Worked: rows 1 and 3 are 16 and 14; columns 1 and 3 are 16 and 15. Row 3's 14
matches neither, so the column with the blank must be the one it matches:
9 + ? = 14, so ? = 5. Then rows 16, 15, 14 against columns 16, 14, 15 — each row
with exactly one column.

**The rule is worth reading twice, and the builder checks it literally**: for
every row, exactly one column has the same sum. Not "the row sums are a
permutation of the column sums", which is a different and stronger claim; and not
"some column", which would leave the answer loose. `SumSquare.holds?` is that
sentence in three lines, and every candidate value is tested against it.

**Two answer formats, one type** — 80 problems, topic `Логически задачи`, area
`interactive_kangaroo`, both over one `SumSquare` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `logic.sum_square_missing` | typed + `figure:` | 1000–1500 (6) | the one missing number |
| `logic.sum_square_fill` | `grid_fill`, no figure | 1150–1540 (4) | two missing numbers, written into the square |

**How a square is built.** Backwards from the rule: pick distinct row totals,
give the columns the same numbers in another order — then every row matches
exactly one column because the totals are all different — and fill the cells to
those margins. The totals are picked *around the middle* of what the cells can
hold; a row summing near the maximum forces cells at the maximum and there is no
room left to make the square look random. The fill starts from ones and hands out
the surplus one at a time to a cell picked at random among those that can still
take it, which keeps every entry inside the rung's range. (The first version used
the north-west corner rule and produced squares with a 14 in them where the cap
was 10 — a third of the rungs came out empty, which is how it was noticed.)

**The step that settles it** is generated, not hand-waved, and there are two
shapes of it. Either a known row's sum matches none of the *known* columns — then
it must be matched by the column holding the blank, and that fixes the blank — or
every known row is already matched, and then the row holding the blank must match
one of the known columns. The explanation prints whichever applies, with the
numbers of that square; a draw where neither applies is rejected rather than
explained badly.

**The ladder** — a bigger square, then bigger numbers:

| Elo | square | numbers up to | blank |
|---|---|---|---|
| 1000 | 3×3 | 10 | the centre |
| 1100 | 3×3 | 12 | anywhere |
| 1200 | 3×3 | 20 | anywhere |
| 1300 | 4×4 | 12 | the middle |
| 1400 | 4×4 | 15 | anywhere |
| 1500 | 4×4 | 25 | anywhere |

`logic.sum_square_fill` starts at 4×4 and never has more than two blanks, and
that is a property of the rule rather than a choice: in a 3×3 with two holes the
rule rarely settles the answer — three rows do not constrain enough — while a
bigger square has more rows each demanding exactly one column, so the pair comes
out forced. Five by five is the widget's ceiling (§3.3).

**The check, and a bonus in it.** The families settle uniqueness by trying values
up to a limit of their own, and the risk in that is a second answer *above* the
limit, which would make the stem's promise false. So the verification walks 1 to
80 instead — and reads each square back out of its own **stem** rather than from
the generator, which means it also proves that the numbers the question states are
the numbers the answer was computed from. 80 squares, one answer each, every one
the recorded one.

**Explanation and hints.** The explanation lists the sums that can already be
worked out, then the deciding step, then the whole rule verified on the finished
square. `check:` says why no other value fits: the blank's column would take a
sum that either appears nowhere among the rows or appears twice. `watch:` is the
trap in the wording — "exactly one column" also forbids two, so a value that
makes two sums agree is wrong however well it fits otherwise. The hints are the
method: *work out the sums you already can*; then *look for a row whose sum is
missing from the finished columns*; then *that column must have exactly that sum,
and the blank follows by subtraction*.

**The figure** — `Figures.number_square(rows:)`: thin inner lines, a heavy border
and the numbers centred, with a `nil` cell printing as a red `?`. The `grid_fill`
family needs no figure at all, since the widget draws the square it asks to be
filled — but its stem still spells the square out, because the importer keys
questions by their text and a widget's contents are not in it (§3.3).

## 5n. How many times the striking clock rings (Кенгуру, without a figure)

**Status: written, not generated.** The two families and the `Chimes` module are
in `families/interactive_kangaroo.rb`; there is no figure at all. Neither family
is in `db/seeds/ladders` or the bank. Verified by running them — 80 problems, ten
full rungs — and every window counted a second time, minute by minute (below). To
ship: `build.rb`, `check.rb`, import — no rasterizing needed.

The type: a clock strikes the hour on the hour, and once, twice, three times at a
quarter past, half past and a quarter to. How many strikes between two moments?

```
# На всеки кръгъл час часовникът в кухнята на баба звъни толкова пъти, колкото е
# часът… 15 минути след кръгъл час звъни веднъж, половин час — два пъти, а 45
# минути — три пъти. Колко пъти ще звъни часовникът тази сутрин във времето от
# 6:50 до 11:20 часа?                                                    → 70
```

Worked: the hours inside are 7, 8, 9, 10, 11 — that is 45 — and the quarters add
1 + 2 + 3 = 6 for each whole hour inside, four of them, plus the lone 11:15.
45 + 24 + 1 = 70.

**Two things make this a problem rather than a sum**, and both are what the
builder is careful about:

1. **The count runs 1 to 12 and starts again.** A window across noon goes 11, 12,
   1, 2, and at midnight the clock strikes **twelve**, not nothing. Which rungs
   carry that is a decision, not an accident: the first two never cross noon, the
   rest always do, and the top rung crosses midnight. A draw on the wrong side of
   that is rejected.
2. **The ends of the window have to be looked at one at a time**, so an end is
   never itself a striking moment. „От 7:00 до 9:00" would leave the reader
   guessing whether those two strikes count, and the answer would depend on the
   guess — the generator refuses any window whose end falls on a quarter.

**Two answer formats, one type** — 80 problems, **no figures**, topic
`Текстови задачи`, area `interactive_kangaroo`, both over one `Chimes` module:

| family | format | rungs | what it asks |
|---|---|---|---|
| `count.clock_chimes` | typed | 900–1450 (6) | how many strikes in the window |
| `count.clock_chimes_split` | `blanks` | 960–1320 (4) | the hour strikes and the quarter strikes separately |

The split is the method made visible: the hours are added as numbers, the
quarters go six to a whole hour, and `check:` divides the quarter count by six to
show it. This is the second type in the catalogue that needs no image at all
(after `logic.lattice_rectangle_pick`, §5l) — here because the question is two
sentences of rules and two times, and a picture of a clock face would say nothing
the words do not.

**The ladder** — a longer window, then the trap, then the trap at midnight:

| Elo | window starts | length | crosses |
|---|---|---|---|
| 900 | 5–7 | 2½–4⅓ h | nothing |
| 1010 | 5–7 | 4–5½ h | nothing |
| 1120 | 9–11 | 3⅓–5½ h | noon |
| 1230 | 9–11 | 5½–8⅓ h | noon |
| 1340 | 8–11 | 8⅓–12⅔ h | noon |
| 1450 | 20–22 | 4⅓–7 h | midnight |

**The check.** Each window is read back out of its own **stem** — so the check
also proves the times the question states are the times the answer was computed
from — and then counted the dumbest way there is: walk the window a minute at a
time, adding the hour count or 1, 2, 3 as the minute falls. 80 windows, no
disagreement, none with an end on a striking moment, and the same routine
reproduces the sheet's own 70 for 6:50 to 11:20.

**Explanation and hints.** The explanation splits the count in two: the hours
listed and added as numbers, then the quarters as "so many whole hours × 6" plus
whatever the two ends leave over, named one by one. `check:` states which strike
is the first and which the last, since that is where the mistakes live. `watch:`
is the 12-cycle when the window crosses it, and otherwise the ends. The hints are
the method with no number in them: *count the two kinds separately*; then *the
hour strikes need the sum of the hours inside*; then *each whole hour adds
1 + 2 + 3, and only the two ends need care*.

## 7. Recipe: add a family

1. Pick the file by area (`families/interactive_number.rb`, `families/geometry.rb`, …).
2. Choose a topic from `db/seeds/topics.yml` (the tree is fixed; no new topics).
3. Choose rungs: start where the type first makes sense, step 60–150 points.
4. Draw parameters with `c.by_level([...])` so difficulty rises with the rung.
5. Reject impossible or silly draws with `raise Authoring::Duplicate` (a ladder
   with a 178 m ladder in it is worse than a shorter ladder).
6. Write the explanation with `Explain.build(idea:, steps:, answer:, check:, watch:)`.
   `watch:` names the mistake the problem is designed to catch — the student
   only ever sees the explanation after getting it wrong.
7. Add a hint ladder with `hints: [...]` — 2–3 rungs, cheapest nudge first, and
   **none of them the answer**. A hint is read *instead of giving up*, an
   explanation *after* getting it wrong; they are not the same text at two
   lengths. The shape that works: the rule or method (no numbers), then the
   first concrete move with this variant's numbers, then the last rung that
   leaves exactly one step for the student. `check.rb` rejects a rung that
   contains the typed answer, or that names a blank and its value close
   together. Imported ladders reach students without further review, so a
   leaked answer ships silently — write the rungs as questions where you can
   ("колко остава за тази клетка?") rather than as statements.
8. Rebuild, check, import:

```bash
ruby tools/authoring/build.rb          # regenerate the YAML
tools/authoring/rasterize.sh           # only if figures changed
ruby tools/authoring/check.rb          # validation
bin/rails problems:import FILE=db/seeds/ladders
bundle exec rspec spec/services/ladder_corpus_spec.rb
```

## 8. Recipe: add a widget

1. Checker + display in `app/services/widgets.rb` (the solution must be
   decidable from the submitted state alone).
2. Stimulus controller in `app/javascript/controllers/widgets/`, registered in
   `controllers/index.js`. Leave the hidden `state` field **empty until the
   answer is complete** — that is what keeps the submit button honest.
3. Partial in `app/views/widgets/_<key>.html.erb`; shuffle anything whose order
   could leak the answer.
4. Hints in `config/locales/app.bg.yml` and `app.en.yml`.
5. A demo in `app/views/design_system/show.html.erb`.
6. Specs in `spec/services/widgets_spec.rb`; validation in `tools/authoring/check.rb`.
7. A builder in `tools/authoring/lib/widget_kit.rb`.

The admin form can only build `QuestionFormParams::EDITABLE_WIDGETS`
(number line, ordering, fraction bars). Questions using the other widgets keep
their grading when edited in the form, so nothing is lost — but the parameters
are meant to be generated, not typed.

## 9. Quality rules (what `check.rb` and the specs enforce)

* **Unique text.** The importer keys questions by their text; two problems with
  the same stem are one problem. Put the numbers in the stem, always.
* **Parseable answers.** Typed answers must match `ExactValue`'s grammar.
* **Distractors are mistakes**, not noise: the off-by-one, the forgotten carry,
  the sum instead of the product.
* **Explanations**: at least 120 characters, numbered steps, a check line, and
  where possible a `watch` line.
* **Typography**: `−` (U+2212) in text, ASCII `-` in answers, decimal comma,
  `·` for multiplication, `:` for division.
* **Realism**: no 178 m ladders, no cyclists at 140 km/h, no ten-hour films.
  Cap the ranges instead of letting the top rung run away.
* **Reachability**: number-line answers on the step grid, dial angles on the
  dial's step, plot points inside the plane, grid counts inside the grid.
