# Question content, widgets and the admin bank

Content model: `Question#body` is a restricted ProseMirror-style JSON document (paragraph/text/bold/italic/math/hardBreak) rendered server-side by `RichContent` (KaTeX renders math client-side via the `math` Stimulus controller, except a `math` node that is nothing but a fraction of integers, which `RichContent` sets with the `.frac` stacked fraction instead — see the notation note below); `body_text` is the plain-text projection. Problem files are written in plain text, so `RichContent.text_to_doc` promotes every bare fraction in it (`RichContent::FRACTION`, guarded so `0,5/2`, `1/2/3` and `km/h` are left alone) to a `math` node: "1/2" is not how a fraction is written in a maths problem. `node_text` reverses it, so `body_text` still reads exactly as the source line — which matters, because that string is what the importer dedupes on and what `problems:export` writes back. Existing rows only gain the math nodes when their file is re-imported (`rake problems:import FILE=db/seeds/ladders/`, idempotent). `answer_type` enum: `multiple_choice` (options in `possible_answers` with a `correct` flag), `exact_value` (graded by `ExactValue` — fractions/decimals/percent/BG-comma equivalence, tolerance; `parse` stays strict because it also validates stored answers and suggestions, while the *given* side goes through `ExactValue.readings`, which reads an answer the way school writes it — thousands spaces, `x = 72`, a unit or a word around the one number, `8!`, and a percent either way — and never guesses when there is more than one number; about one "wrong" answer in six in the family field test was one of these), `interactive` (widget state graded server-side by the `Widgets` registry — the solution never reaches the client). Twenty-one widgets ship: `number_line`, `angle_dial`, `clock_hands` and `coordinate_plot` place a value; `ordering` (dragged by its grip — on the right of the row, and it is the grip rather than the whole row that a finger drags, so the list does not swallow page scrolls — with pointer events, since no touch browser implements HTML5 drag and drop), `categorize` and `matcher` arrange; `multi_select` chooses; `blanks` and `grid_fill` fill in; `fraction_bars` and `grid_shade` shade (exact cells, any N cells, or a solid rectangle of two sides either way round, optionally pinned to the top-left corner — „правоъгълник 3 на 4“ does not say which side runs across). Seven more show the working rather than only the result: `column_arithmetic` (written addition and subtraction — only the result row is graded, the carry/borrow cells above it are stored as the child's working), `balance_scale` (an equation as two pans, moved by doing the same to both sides; the moves are replayed by `Widgets.balance_after` for display but the *typed* x is what is graded, because a scale that only allows legal moves cannot be got wrong and a widget nobody can get wrong measures nothing), `geoboard` (a polygon drawn on pegs, graded by rule — shape, area, perimeter via `Widgets.polygon_facts` — so any fitting rectangle anywhere on the board is right; the solution carries one example under `points` for the checks), `unit_circle` (angles as a set modulo 360°, sine/cosine readouts only when the question does not ask for them), `find_mistake` (the line of a worked solution where the mistake is made), `number_hops` (an open number line: the hops must be sizes on offer and add up to the change, and the landing number is typed — the landings show „?“, never the sum) and `inequality_line` (boundary, filled or open dot, direction, all chosen explicitly). `equal_parts` is the geometry one: a figure with one segment or angle highlighted, and the child taps every part the construction makes equal to it (the other half a perpendicular bisector cuts, the halves of a bisected angle, the angles a transversal makes equal), graded on the exact set. Its part ids are masked like an ordering's, the given part's too, and `check.rb` refuses a figure that has no decoy drawn within 4% of the given part (12% was tried, and "pick whatever looks equal" scored 237 of 239; the answer parts are also drawn deliberately unequal, which keeps the coordinates in the markup from giving them away), because a figure drawn to scale would let a child pick the equal parts by eye. It brought the leaf topic „Еднакви триъгълници“ (prerequisite „Ъгли“, 7th grade in `Curriculum`), the НВО 7 staple the app's own „what we are working on“ list had named as missing. Their problems are the `working.*` families in `db/seeds/ladders/interactive_working.yml`; `check.rb` loads `app/services/widgets.rb` itself for the balance and polygon rules rather than keeping a second copy. In `grid_fill`, `nil` is a blank and `""` is a cell outside the puzzle (a pyramid's corners), drawn empty and never asked for. A `grid_fill` with `layout: "pyramid"` (the addition pyramids, `puzzle.addition_pyramid`) is drawn the right way up — rows bottom-up, centred and staggered so each cell sits between the two it is the sum of, the `""` padding left out — on the problem and on the answer screens alike; as a left-aligned table it was upside down with every cell straight over one other, which a student reported (2026-11-08). `operation_chain` draws the first-grade СМТ puzzle of two operations (`tl op tr = m`, then `m op r = b`): a worked example in a dashed frame, then each chain with the number tiles it may use, its empty squares the answer boxes (`"<chain>.<place>"`, graded like `blanks`). Only a past paper uses it (СМТ 2016, 1 клас, задача 7, which had been seven questions over the paper's picture with its arrows described in words), so `ladder_corpus_spec` counts the past papers' widgets too when it checks that every widget has problems behind it. Both are answers made of boxes in a drawing (`WidgetAnswersHelper::DRAWN_ANSWERS`), so the feedback card, the answer page and a report thread's question card draw them back — `answers/_grid_fill_review`, `answers/_operation_chain_review`, each box marked right or struck through with the right value — never as the one-line `display` string, which for a chain read „2, 2, 4, 3, 1; 4, 1, 3, 2, 5“. Item ids never reach the page as written: an ordering's ids are in answer order, a matcher pairs `l0` with `r0` and a multi-select often lists the right options first, so `Widgets.masked_params` gives the page an HMAC token per item (keyed to the question) and `Grading` runs `Widgets.unmask_state` before grading — the stored state keeps the real ids, so history and past answers are untouched. Each is a checker plus display in `app/services/widgets.rb` (plus a `solution_display` where the stored solution isn't shaped like a finished state — `multi_select` keys it `correct` rather than `selected`, and a counted `grid_shade` names no cells at all, so both would otherwise show an empty „верен отговор“ chip), a Stimulus controller in `app/javascript/controllers/widgets/`, a partial in `app/views/widgets/`, a hint string in the locales and a demo on `/design-system`. The authoring form can only build `QuestionFormParams::EDITABLE_WIDGETS` (number line, ordering, fraction bars); a question using any other widget keeps its stored grading when edited there, because those parameters are generated with the problem rather than typed, `free_text` (reserved, Phase 3 AI grading). `grading` jsonb holds expected value/widget params+solution. `status` enum: draft/private_library/in_review/published/retired — only published questions enter practice. `retired` is the end of a question's life (the „Архивирай“ button on the admin edit page, `Question#retire!`): never asked again, but kept so every answer given to it still shows its problem in the student's history, and a re-import leaves it retired. Leaving `published` by any route — retiring, or the report queue's withdraw to draft — also drops the question's *unanswered* rows from sessions already composed (`Question#leave_unfinished_sessions`): a placement gets its next question picked instead, a session left with nothing unanswered is finished, an empty one is deleted. A question can carry one image on its polymorphic `attachable` (`QuestionImage`, an Active Storage attachment shown above the body in the practice, duel and preview views). Legacy `text`/`answer` columns remain nullable until grading parity is confirmed in production, then drop.

The admin side of the bank is a **browser and an editor** (`Overseer::QuestionsController`). The browser is one search bar with removable tokens over `QuestionFilter`, which owns the whole query: facets (an area stands for its leaves, each facet counted with its own filter lifted), an Elo range over a fixed-axis histogram of the result, „has" filters, saved views counted over the whole bank — published, with an active report, „Много пропускани" (skip share over `SKIPPED_SHARE` out of at least `SKIPPED_MIN_ANSWERS` answers), without hints, retired — and the sorts, which are columns of one derived table so the page, a template's representative and the editor's neighbours all read the same order. There is deliberately no „too easy for its Elo" view: saying so honestly needs each answerer's rating *at the time*, which nothing stores, and a question that is too easy already loses Elo with every answer. „Групирай по шаблон" collapses rows by `SessionComposer::SHAPE_SQL` with a window count. Every row's right/wrong/„не съм го учил" bar comes from `QuestionStats.for` — one grouped query over `user_answers` for the page's ids, a `pending_review` answer counted as none of the three. Choosing a row swaps only the `question-pane` turbo-frame (the index answers that frame request without running the list), ↑/↓ walk the rows and E opens the editor. The editor carries the list it came from as `from[...]`, which is how its sticky bar says „3 от 214" and „Запази и следваща" goes where the list would (the neighbour is taken *before* the save, since a save can move the question out of the list or along it); a ticket's `return_to` still wins. It folds in the hint ladder — `QuestionFormParams.save_hint!` keeps `reviewed_at` meaning „a human approved these words", refuses a rung containing the answer by `check.rb`'s rule, and the old `/overseer/questions/:id/hint` page redirects to the section — warns before an option somebody already chose is reworded or removed (`QuestionStats.option_choosers`: their answers keep their verdict and their stored wording, so the two quietly stop matching), and shows how students fare with the most common wrong answer. Saving a question also re-grades the answers already given to it (`AnswerRegrade`): any wrong answer the question now accepts becomes right, with the XP it was owed (a `regrade` XP event) and off „За преговор" — only ever wrong → right, and ratings are left alone since an Elo game cannot be replayed out of order. `rake answers:regrade` (`DRY_RUN=1` to count) does the same over every question, run once when the grader learns something. The form's always-present empty option row is dropped in `QuestionFormParams.kept_options`: its hidden „correct" value used to get past `reject_if: :all_blank` and fail every save of a non-multiple-choice question. Every admin create, save, hide, retire and restore writes a `question_revisions` row holding only the fields that moved, as [before, after] in the editor's own terms (`QuestionRevision.snapshot`: text, options, accepted answer, explanation, Elo, topic names, status, hints) — so a skip rate or a report can be read against what the question said last week. An imported question has none and its history card says „Импорт": its history is the problem file's, in git. The starting Elo of a question is not known (nothing stores it), so the editor shows where the topic's other published questions sit instead.
